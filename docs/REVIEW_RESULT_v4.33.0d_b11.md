## 4. 저장소·실행기·Keeper의 나머지 질문

### 저장소와 쓰기 수렴

- 목록 실패는 종류별 unknown으로, `arb/` 실패는 asks까지 전파한다. 파일 읽기·JSON 문법 해석 실패는 file:<경로>로 남기고, grant 읽기 실패는 grant도 막는다. timeout 시험은 모든 관련 종류를 모름으로 만든다. 목록 실패 때 캐시를 꺼내 빈칸을 채우는 경로는 없다. 단, Q7의 잘못된 자료형은 별개다.
- 수정 시각·크기가 같으면 캐시를 재사용하고 600초마다 비운다. 같은 메타데이터로 내용만 바뀌는 경우는 다음 전체 읽기까지 감지하지 못한다. 이것을 새로운 정합성 보장으로 해석해서는 안 된다.
- apply_writes는 StoreError에서 멈춘다. 통합 시험의 잠금 중간 쓰기 실패, 1a의 모든 prefix 중단 시험과 추가 RunChoice 12개 경계는 수렴했다. 실제 원격 쓰기가 접수된 뒤 응답만 끊긴 상황의 모든 조합을 실측한 것은 아니다.
- RcloneStore의 create_only는 exists→rcat이며 원자적이지 않다. 심판만 판정 파일을 쓰고 고유 ID의 보고만 각 실행기가 쓰는 계약 안에서는 기존에 인정한 비교/쓰기 사이 틈으로 본다. 이 틈 자체를 새 결함으로 보고하지 않는다. 충돌 시 다른 내용이 들어 있음을 검증하는 CAS 기능이 생기는 것은 아니다.

### rclone 문서 대조

- 경로 앞 `/`가 없는 include 이름을 하위 파일 이름에도 적용하는 방식과 여러 include의 사용에서 문서상 확정적인 오류는 찾지 못했다. `-R`, `--files-only`, `--metadata`의 조합은 제어 파일 목록을 얻으려는 의도와 맞는다. [공식 필터 문서](https://rclone.org/filtering/) 기준이며 실제 원격 실측은 하지 않았다.
- Drive 메타데이터의 owner는 보통 이메일, btime은 생성 시각이며 `metadata_owner` 기본값은 read다. 현재 키 이름은 문서와 맞는다. [공식 Drive 메타데이터 문서](https://rclone.org/drive/#metadata), [owner 옵션](https://rclone.org/drive/#drive-metadata-owner).
- 운영 전에는 rclone 버전·설정을 고정해 G 소유 grant와 사람 소유 신호를 실제 출력에서 확인해야 한다. owner가 빈 경우 접수는 막히지만, btime이 빠질 때 ModTime으로 대체하면 ‘만든 뒤 수정’ 검사의 근거가 없어지므로 이 대체값을 검증된 생성 시각으로 취급하지 않는 조건이 필요하다. 공유 드라이브·소유자 없는 파일까지 일반화하지 않았다.
- stderr의 directory not found를 빈 폴더로 보는 구현은 초기 미생성 폴더용이다. 접근 권한 상실·경로 오설정까지 같은 것으로 보지 않는지는 배포 전 원격 시험에서 확인할 항목이다.

### 실행기 계약

- 현재 보고 생성부는 TASK end·stop·confirm, read 게시, run 완료의 필요한 식별 묶음을 채운다. 새 gen·epoch를 보고 키에 포함해 재발급 뒤 다시 보고한다. 마스터 교체 통합 시험에서 CVAT import가 TASK당 한 번이었다.
- 승인 전 commit은 호출하지 않고, 처리 중 오류·권한 상실 뒤 같은 TASK의 commit을 다시 호출하지 않는다. 정상 완료 출력을 메모리에 보존해 보고 쓰기 재시도가 곧바로 CVAT 재호출이 되지 않도록 했다. 승인 전 CVAT 쓰기를 시도한 처리기는 권한 검사로 실패한다.
- 취소·정지 시험에서 준비 중 취소는 canceled, 정지는 묶음 반납 뒤 신규 배정 차단으로 이어졌다. 승인 뒤 CVAT 호출 사이 권한 상실은 import·restore를 막았다. 새 세션은 옛 세션 배정을 실행하지 않고 심판의 승인 전 회수/승인 뒤 격리에 따른다.
- 처리기가 ctx.auth를 생략하는 문제와 CvatFactory·실제 timeout·서버 조회 연결은 요청에서 정한 2단계 전제다. 그 연결이 이미 끝났다고 판정하지 않았다. Q1·Q2는 그 전제와 별도로 뼈대 자체에서 확인한 문제다.

### Keeper 자격·감시·비밀

- 살아 있는 회차가 있으면 다른 신청자에게 자격을 넘기지 않고, 갓 부여한 자격에는 첫 회차의 유예를 둔다. 기존 시험의 두 마스터 예에서 불필요한 왕복은 없었다. 다만 회차가 정지한 현재 소유자만 계속 heartbeat·신청을 유지하면 같은 소유자를 새 epoch로 계속 선정할 수 있으므로, 실제로 판정 회차가 회복됐는지를 별도로 감시해야 한다.
- 기동 중 커널 상태 조회 입력은 Keeper에 아직 없다. heartbeat가 나타나기 전의 Kaggle 대기/실행 중을 확인하지 못한다. 2단계의 실제 기동 감시와 함께 연결하고, 자동 깨우기(auto.json)도 수동 신호와 동일한 제한 횟수·시도 ID의 재시도 계약으로 다뤄야 한다. 현재 자동 경로는 매번 attempt=1을 만든다. 운영의 주간 상시 유지와 ‘한 번만 재시도’의 적용 단위를 명확히 해야 한다.
- Kaggle 키는 Script Properties에서 읽고 HTTP Authorization에만 넣는다. 응답 본문·예외 원문은 기록하지 않고 상태 코드/고정 사유만 남긴다. 가짜 Drive·메일 시험에서 키가 남지 않았으며 doGet/doPost가 없다. 승인 노트북 해시 불일치 시 push를 막는다. 메타데이터와 scripts의 편집 권한은 배포 신뢰 경계에서 확인해야 한다.

- 설정 저장소 장애에서 새 권한 판단을 중단할 때 기존 승인 작업을 어디까지 마무리할지. 현재 최대 10분 권한 회수 약속과 무기한 옛 캐시 사용은 양립하지 않는다.
- 주간 상시 자동 기동에서 ‘한 번 재시도’의 적용 단위와, 연속 기동 실패 뒤 운영 알림·다음 자동 시도를 허용하는 조건.
- rclone 지원 버전·소유자/생성 시각 누락 시 정책과 실제 배포 계정/Drive 형태. API·메타데이터 실측은 별도 운영 시험으로 남긴다.

## 7. 보지 못한 항목·제한

- 실제 Drive·Apps Script·Kaggle·CVAT 접속 및 실측은 하지 않았다. rclone 명령의 문서 대조만 했다.
- 정식 Node.js 명령은 환경 제약으로 완료하지 못했다. V8 대체 실행은 위 제한을 갖는다.
- 2단계의 실제 처리기 이전·노트북/셀/GPU 연결, 저장소 밖 앱·ULD앱, F7·F8은 범위 밖이다. 백업·라벨 보호의 실제 CVAT 경로는 연결 후 다시 검토해야 한다.
- 기존 v4.32 전체 회귀 시험·모든 노트북 셀의 동등성·설계 8판의 다른 절 전면 재검토는 하지 않았다.
- 모든 원격 장애/경합 조합을 증명한 것은 아니다. 이번 시험 통과와 반례 해소의 판정은 명시한 가짜 저장소·현재 함수 경로에 한정한다.
