# 가지 앱 경합 통제 설계표 8판 (v4.33)

2026-11-14 · 재웅님 · 7판 검토(b7: L1~L3), 구현 1a, K 계정 rclone 확인 결과와 11/14 결정을 반영 · **8판 보충**: 1a 코드 검토(b8: M1~M12, b9: N1~N5, b10: P1~P3)와 1b 구현에서 정한 판정 계약 ('보고·결과·인계 계약' 절)

- **Drive의 파일 소유자는 rclone 토큰의 Google 계정**으로 정해집니다. 어느 Kaggle 계정에서 실행했는지는 Drive에 보이지 않습니다 (11/14 시험). 그래서 Kaggle·Colab·앱이 만드는 파일은 모두 A0 소유이고, 소유자로 구별되는 것은 G뿐입니다.
- 공유 폴더는 A0가 소유하고 G에 편집자 권한을 줍니다.
- **A0 Kaggle 보조 실행기:** 다른 실행기와 같이 배정·잠금·권한 확인을 따르고 `deploy/`에서 검증된 노트북만 돌립니다. 사람이 켭니다 (Keeper·마스터는 K의 Kaggle만 켬). 실행 환경 능력(`caps`)에 `colab_oauth`가 없으므로 23번 같은 Colab 전용 일은 받지 않습니다. 심판(마스터)은 K에서만 돌립니다.
- **CVAT 계정은 하나**입니다. 실행기·수집기·ULD앱·사람의 CVAT 웹 작업이 CVAT 기록상 같은 사용자입니다. 구별은 우리 쪽 기록(접수·단계·의도 기록)으로 합니다. CVAT 토큰을 바꿀 때는 Colab(A0)·Kaggle(K·A0)·수집기(G)를 함께 바꿉니다.
- **관리자 전용 폴더:** `deploy/`와 정책 `config/`(people·accounts·routing·min_version)는 공유 폴더 밖 `eggplant_admin/`(A0 소유)에 두고, G에는 보기 권한만 줍니다. 실행 중 바뀌는 시험 설정은 여기 두지 않고 공유 폴더 `sets/test_tasks/`에 둡니다 (L1). 코드·앱은 정책 루트와 데이터 루트를 섞거나 옛 공유 `config/`로 되돌아가 읽지 않습니다.

### 세션 지문 (8판)

| 항목 | 규칙 |
| --- | --- |
| 믿음의 시작점 | **G 소유 자격 파일** `jobs/ARBITER_GRANT.json` (세션·epoch). G는 소유자가 다르므로 소유자 확인이 유효합니다 |
| 세션 ID | `<환경>-<기계 지문>-<시작 시각>-<난수>` (예: `kgl-3fa91c2e-11140408-7k2q`). 기계 지문 = 호스트 이름 + 부팅 ID의 해시 8자 |
| 생존 신호 | `workers/<세션>__<지문>.json` |
| 판정 파일 표시 | 심판이 쓰는 모든 파일(`arb/**`, `CURRENT.json`, 복구 요청)에 `by_session`·`by_epoch` |
| 실행기·심판이 판정 파일을 믿는 조건 | `by_epoch`가 자격 epoch보다 크지 않고, 같은 epoch이면 `by_session`이 자격의 세션. 표시가 없으면 따르지 않음(알림). 옛 epoch 파일은 새 심판이 다시 발급 |
| 중복 세션 | 같은 세션 ID가 서로 다른 지문으로 살아 있으면(노트북 사본 동시 실행) 그 세션에 일을 주지 않고 알림 |
| 복구 요청 | 심판의 신호 계획이 있고 `by_session`·`by_epoch` 표시가 있는 것만 '시스템(심판)' 요청자로 접수 |

**이것은 증명이 아닙니다 (L2, 결정 가).** 세션 지문과 소유자 확인은 실수(옛 마스터의 늦은 쓰기, 손으로 만든 판정 파일, 노트북 사본 동시 실행)를 걸러내는 장치입니다. 같은 Drive를 쓰는 누군가가 일부러 표시를 맞춰 쓰는 것은 막지 못하며, 이는 신뢰 모델이 받아들인 범위입니다. 내용까지 인증하려면 서명 키가 필요하므로 지금은 두지 않습니다.

### 요청자는 처음 접수 때 정함

- 심판은 요청을 처음 볼 때 소유 계정을 사람에 연결하고, 접수 기록(`arb/intake/<요청ID>.json`)을 남깁니다. 그 뒤 상태 이름이 바뀌거나 다시 게시돼도 요청자는 접수 기록을 따릅니다.
- **배정할 때는 지금 people로 권한을 다시 확인합니다.** 접수 뒤 `stopped`가 되었거나 권한이 빠진 사람의 대기 요청은 배정하지 않습니다 (이미 받은 실행은 '알려진 한계'대로 그 일이 끝날 때까지 유지).
- 접수 기록이 없는 요청은 실행하지 않습니다.
- **사람이 늘어날 때의 조건:** 지금 앱은 A0로 파일을 만듭니다. 사람을 추가하기 전에 앱이 사용하는 사람의 계정으로 파일을 만들도록 바꿔야 합니다.

분석 모드를 지키는 장치:

- **CVAT 접속 factory:** 모든 CVAT 접속(SDK client, 하위 API, 백업 스크립트의 자체 세션)은 한 factory에서 만듭니다. 분석 모드에는 **허용 동작 목록**(읽기, 참조용 export 준비·받기)만 통과하는 감싼 객체를 줍니다. 메서드 이름 추측이 아니라 허용 목록으로 정합니다.
- **입력과 출력 분리:** 공유 폴더는 읽기 입력(BASE)이고, 분석 결과는 출력 폴더(`analysis/<M>/<날짜>_<세션>/`)에만 씁니다. 모든 저장은 출력 위치를 받는 저장 도우미를 거칩니다.
- **좁은 예외:** 분석 사용자도 요청 만들기, 확인 결과 신호, 자기 `workers/` 생존 신호는 씁니다. 이것은 별도의 좁은 API로만 씁니다.
- **'이 결과 올리기':** 결과를 **고정 제출본**으로 복사해 보냅니다 (아래 '이 결과 올리기' 절).

| 생존 신호 스레드 | 60초마다 `workers/<마스터>.json` | ARBITER를 쓰지 않음. 판정 루프가 마지막으로 끝낸 회차 번호를 함께 적음 |
| CPU 작업 프로세스 | 백업·export·받는 중 확인·취합·관리 일 중 CPU 일 | `python -m worker_cpu --run <실행ID>`. 자기 임시 폴더·세션 ID·생존 신호. 다른 실행기와 같은 규칙 |
| GPU 기동 | GPU 대기열을 보고 Kaggle GPU 작업자를 켬 | Kaggle 상태 조회·push는 판정 루프를 막지 않게 작업 프로세스에서. GPU 대기열 작성자는 마스터 하나 |

판정 루프 한 회:

1. **자격 확인:** `ARBITER_GRANT.json`의 세션·epoch가 내 것인지. 아니면 판정을 멈추고 작업 프로세스에 새 일을 주지 않음.
2. **입력 읽기:** 요청 폴더 2개, `arb/ask/`, `workers/`, `jobs/signals/`·`arb/signal_done/`, `CVAT_UpLoader/requests`·`locks_ask`·`workers`, `config/min_version.json`·`routing.json`. 수정 시각 목록으로 바뀐 것만 읽고 10분마다 전체를 읽음.
   **신원 확인 (J9·K3):** 새 요청·신호마다 Drive 소유 계정을 읽어 '계정과 신원' 절의 허용 입력 표로 판단하고, 요청은 접수 기록을 남깁니다. 파일 안에 적힌 사람 번호는 믿지 않습니다. 허용되지 않은 계정이거나 `stopped`이거나, 그 동작의 권한이 없으면 거절하고 기록합니다. 소유 계정을 못 읽으면 그 입력은 '모름'입니다.
3. **'모름' 판단:** 자격·요청 목록·`workers/` 목록 중 하나라도 못 읽으면 이번 회는 **새 승인·회수를 하나도 하지 않음**(보고 반영만). 개별 파일만 못 읽으면 그 대상만 미룸. 같은 대상의 '모름'이 30분 넘으면 알림.
4. **보고 반영:** 확정 신청·확정 끝·반납·결과 보고·멈춤 보고를 먼저 반영.
5. **만료:** 생존 신호가 3분 끊긴 실행기 — 확정 승인 전이면 회수·재배정, 확정 승인 뒤면 '확인 필요'로 격리.
6. **신호·취소:** 신호 처리 (아래 '신호').
7. **배정·허가:** 차례에 따라 요청 묶음·TASK 잠금·관리 일을 정함. decision ID 하나로 `assign/`을 먼저 쓰고, 잠금 파일에 같은 decision ID·epoch·실행기 S·gen을 적음.
8. **확정 승인:** 확정 신청 중 현재 소유·epoch·gen·decision ID·취소 상태가 모두 맞는 것만 승인.
9. **정기 점검:** 10분마다 '감시와 재시작 점검'의 대조를 가볍게 실행.
10. **회차 기록:** `arb/ARBITER.json`에 epoch·회차·시각·처리 수·'모름' 목록, 그리고 **깨우기 정보**(받는 중 수·다음 확인 시각, 남은 묶음 수, 취합 필요, 처리 안 된 정지).

심판 자격:

- 마스터는 켜지면 `jobs/arbiter_ask/<S>.json`을 씁니다.
- Keeper(U2)는 1분마다 확인하고, LockService 안에서 살아 있는 심판이 없을 때만 `ARBITER_GRANT.json`(세션·epoch +1)을 씁니다. '살아 있음'은 ARBITER의 회차가 3분 안에 올랐는지로 봅니다.
- 자격을 잃은 옛 마스터가 늦게 쓴 판정은 epoch가 낮아 실행기가 따르지 않습니다.

재시작 인계 (새 epoch):

- 새 마스터는 첫 회에 판정보다 먼저 **재시작 점검**을 합니다 ('감시와 재시작 점검').
- 이전 epoch의 잠금은 **다시 발급**합니다. 소유 실행기가 살아 있으면 같은 소유자·같은 decision ID로 새 epoch 잠금을 씁니다. 실행기는 이것을 보고 하던 일을 이어 갑니다. 소유 실행기가 죽었으면 확정 전은 회수, 확정 중은 '확인 필요'.
- 다시 발급되기 전의 짧은 틈에는 실행기가 다음 CVAT 호출 전에 기다립니다(아래 권한 확인). 10분 안에 다시 발급되지 않으면 그 실행기는 멈추고 멈춤 보고를 남깁니다.
- 구 epoch가 늦게 정본 경로를 덮어쓴 것을 발견하면, 새 심판이 같은 내용을 새 epoch로 다시 씁니다.

## 실행기 규칙

TASK 하나를 처리하는 순서:

| 단계 | 하는 곳 | 심판과의 관계 |
| --- | --- | --- |
| 1. 받기·추론·결과 만들기 (TASK 전체를 로컬에서 끝까지, shape도 결과 파일로) | 세션 임시 폴더 | 배정·잠금 확인 |
| 2. 확정 직전 다시 검사: TASK 이름·기존 라벨 수·사람 라벨 보호 설정 | CVAT 읽기 | — |
| 3. **확정 신청** | `arb/ask/<S>__<자원>__<작업번호>.json` (매번 새 파일). 요청 ID·묶음 ID·작업번호·epoch·gen·decision ID | 심판이 다음 회에 승인 |
| 4. 승인 확인 | 승인의 decision ID·gen·epoch | — |
| 5. **복구 자료 게시**: 올리기 전 백업, 올릴 결과 파일(해시), 설정, 단계 기록 → `recovery/<TASK>/<작업번호>/`. 다시 읽어 크기·해시 확인 | Drive | 못 하면 CVAT에 쓰지 않고 반납 (G2) |
| 6. 교체·올리기. 실패하면 백업으로 복원 | CVAT | **호출마다 직전에 권한 확인** |
| 7. 이름 바꾸기 (`_uld` → `_uld_AA`) | CVAT | 권한 확인 |
| 8. 산출물 게시·TASK 기록 | Drive | 게시 전 권한 확인. 실패하면 그 자리에서 다시 시도 (최대 10분) |
| 9. 확정 끝·결과 보고·반납 | `arb/ask/` | 심판이 다음 회에 풀어 줌 |

**권한 확인 (G1):** CVAT를 바꾸는 호출(올리기·지우기·복원·이름 바꾸기)과 공유 게시 직전마다 `ARBITER_GRANT.json`과 그 TASK 잠금을 읽어 '소유자 = 나, decision ID = 내 것, 잠금 epoch = 현재 자격 epoch'인지 봅니다.

- 맞으면 진행합니다. CVAT 호출 하나는 10분 한도(`CVAT_CALL_MAX = 10분`)로 끊습니다.
- **확인-호출 틈 재확인 (H1):** 권한 확인을 마친 시각(단조 시계)과 실제 호출 직전 시각의 차이가 5초를 넘으면 권한을 다시 확인합니다. 프로세스가 멈췄다 깨어난 경우를 걸러 내기 위한 것입니다.
- 자격이 바뀌었고 잠금이 아직 다시 발급되지 않았으면 기다립니다 (최대 10분).
- 잠금이 다른 소유자·다른 decision이면 **권한을 잃은 것**입니다. 복원도 하지 않고 바로 멈추고, 단계 기록에 '권한 잃음, 어느 단계'를 남깁니다.

**단계 기록:** 5~8단계는 각 CVAT 호출 전에 '의도', 뒤에 '결과(성공·실패·복원 성공·복원 실패)'를 `recovery/<TASK>/<작업번호>/steps/`에 새 파일로 남깁니다. 결과는 구조화해 `완료`, `실패(복원됨)`, `부분 반영`, `확인 필요`를 구별합니다.

- **보고 식별 (H7):** 확정 신청·승인·확정 끝·반납·결과 보고는 모두 같은 식별 묶음(요청 ID·묶음 ID·작업번호·epoch·gen·decision ID·실행기 S·TASK)을 적습니다. 심판은 묶음 전체가 지금 것과 맞는 보고만 반영하고, 늦게 온 옛 보고는 거절해 기록만 남깁니다.
- 확정 신청부터 확정 끝까지 실행기는 다른 일을 하지 않고, 생존 신호를 계속 보냅니다.
- 8단계를 10분 안에 끝내지 못하거나 확정 중에 끊기면 그 TASK는 '확인 필요'입니다. 자동으로 다시 하지 않습니다.
- 실행기 안의 병렬 줄은 서로 다른 TASK만 맡고, 줄마다 CVAT 접속·작업 설정 객체·세션 기록 파일을 따로 씁니다.
- 묶음 일부만 잠금이 게시된 경우, 실행기는 잠금이 assign과 맞는 TASK만 시작합니다. 나머지는 심판이 다음 회에 다시 발급할 때까지 건너뜁니다.
- 요청의 최종 상태(완료·실패·취소됨)는 그 요청을 배정받은 실행기가 마지막 묶음 뒤 이름 바꾸기로 씁니다. 소유 실행기가 죽으면 심판이 요청을 다른 실행기에 다시 배정하고, 그 실행기가 남은 TASK와 최종 상태를 맡습니다. 사람의 확인 선택은 요청 파일을 직접 바꾸지 않습니다. '확인 필요' TASK가 남은 요청은 '완료'가 될 수 없고 '확인 필요 n건'으로 끝납니다. 복구 일의 결과는 원요청의 그 TASK 결과에 연결합니다.

## '확인 필요' 처리

| 원인 | 앱에 보이는 것 | 사람이 고르는 것 |
| --- | --- | --- |
| 확정 중 실행기 끊김 | TASK, 마지막 단계 기록, 복구 자료(백업·올리려던 결과), CVAT 현재 라벨 요약 | ① 정상 (CVAT가 올리려던 결과와 같음) ② 백업으로 되돌리기 ③ 다시 하기 |
| 복원 실패 | 위와 같음 + 오류 | ② 또는 ③ |
| 권한 잃음으로 멈춤 | 위와 같음 | ①·②·③ |
| 기록 게시 실패 | TASK, 남은 기록 | ① (기록만 다시 게시하는 요청) |
| 관리 일·학습 실행 실종 | 실행 ID, 마지막 단계 기록, 버전 목록 파일 유무와 해시 검증 결과 | ① 끝난 것으로 처리 (버전 목록 검증 통과·decision 일치 때만, 그 뒤 심판이 채택) ③ 다시 하기 (새 실행 ID) |

**고를 수 있게 되는 조건 (G1·H1):** 아래 중 하나가 되어야 앱의 선택 버튼이 열립니다. 15분은 **종료의 증거가 아니라 고를 수 있게 되는 시점**입니다.

| 조건 | 남는 위험 |
| --- | --- |
| 실행기가 '멈춤'을 보고함 (권한 잃음, 복원 실패 등으로 스스로 멈춤) | 실행기는 멈췄지만, 그 전에 서버에 접수된 가져오기는 남을 수 있음 → 진행 중 가져오기 확인 |
| 옛 실행기가 Kaggle 커널이고, Kaggle API에서 그 커널이 끝났음(완료·오류·취소)을 확인 | 서버에 이미 접수된 가져오기만 남음 → 아래 진행 중 가져오기 확인 |
| 생존 신호가 끊긴 뒤 15분(`CVAT_CALL_MAX` 10분 + 여유 5분)이 지났고, CVAT에서 그 TASK의 진행 중 가져오기가 없음을 확인 (조회할 수 있을 때) | 옛 프로세스가 아직 살아 있다가 늦게 쓸 수 있음 (Colab처럼 종료를 확인할 수 없을 때). 아래 '찾아내기'가 일부만 잡음 |
| 위 어느 것도 안 되는데 풀어야 함 → **관리자 강제 해제** | 화면에 "옛 실행기 종료를 확인하지 못함, 늦은 쓰기 가능"을 보여 주고 관리자가 확인한 뒤에만 |

CVAT는 쓰기 요청에 번호를 붙여 낡은 쓰기를 거절하는 기능(펜싱)이 없습니다. 그래서 읽기 확인만으로 옛 실행기의 쓰기를 완전히 막을 수는 없고, 남는 경우의 **일부를 찾아내기**로 잡습니다.

- **승인 없는 쓰기 감시:** 정기 점검이 TASK의 CVAT 마지막 수정 시각(수집기가 모으는 `updated_date`)과 승인된 쓰기 기록(단계 기록)을 대조합니다. 승인된 쓰기 기간 밖에서 바뀐 TASK는 '알 수 없는 쓰기'로 알리고 '확인 필요'로 돌립니다. 사람이 CVAT에서 직접 라벨을 고친 경우도 여기에 잡히므로, 화면에서 '사람 작업'으로 표시해 넘길 수 있습니다.
- **이 감시는 일부만 잡습니다 (J6):** 옛 실행기의 늦은 쓰기가 다른 실행기의 정상 승인 기간 안에 일어나면, 마지막 수정 시각만으로는 구별할 수 없습니다.
- **강제 해제·종료 미확인 TASK의 사후 비교:** 관리자 강제 해제나 '종료를 확인하지 못한 15분 해제'로 넘긴 TASK는, 다음 실행이 끝난 뒤 CVAT의 annotation을 export해 그 실행의 기대 결과와 한 번 비교합니다. 파일 해시가 아니라 **정규화한 내용**(프레임·라벨·좌표를 정렬·반올림한 것)으로 비교하고, shape·track·덧붙임마다 기대 최종 상태를 정합니다. 다르면 '확인 필요'로 돌립니다. 이 비교도 그 뒤의 늦은 쓰기까지 막지는 못합니다 ('알려진 한계').

선택 뒤 심판의 처리:

- 먼저 그 TASK 잠금을 새 decision으로 바꿔 씁니다. 이때부터 옛 실행기는 다음 권한 확인에서 걸립니다 (이미 확인을 마친 호출 하나는 남을 수 있음 — 위 '찾아내기').
- ① 정상: 잠금을 일반 차례로 돌립니다.
- ② 되돌리기·③ 다시 하기: 잠금을 일반 차례로 풀지 않고 **복구 일**(새 요청, 이름은 신호 ID에서 만듦)에 바로 넘깁니다. 복구 일이 끝난 뒤에 일반 차례를 엽니다.
- 그 전까지 그 TASK는 아무에게도 배정되지 않습니다.

## '이 결과 올리기' (G7)

- 앱이나 셀에서 보낼 때, 분석 결과를 `submissions/<M>/<제출ID>/`로 **복사해 고정**합니다. 만든 뒤 바꾸지 않습니다.
- 제출 정보: 해시·크기·형식, TASK ID·CVAT 서버, 프레임 범위·프레임 대응(ULD 프레임맵), 라벨 이름, 모델·설정, 교체/덧붙임 동의.
- 실행기는 제출본을 자기 임시 폴더에 받아 해시를 확인하고, TASK의 현재 프레임 수·라벨 정의와 맞는지 검사한 뒤 그 바이트를 올립니다. 맞지 않으면 실패로 돌려줍니다.
- 다시 계산한 결과는 새 제출 ID로 보냅니다. 분석 폴더 정리는 제출본에 영향을 주지 않습니다.

## 학습 줄과 관리 일

### 학습 줄

- 학습은 **별도의 줄**에서 실행합니다. 관리 일 대기열과 서로 기다리지 않습니다 (11/14 재웅님).
- 같은 모델의 학습은 한 번에 하나입니다 (`arb/locks/train/<모델>.json`). 다른 모델끼리는 GPU 실행기만 있으면 함께 돌 수 있습니다.
- 학습은 시작할 때 쓰는 **데이터셋 버전·시험 TASK 설정 버전·시작 가중치 버전**을 고정해 학습 출처에 남깁니다.
- **시작 때 호환 확인 (b7):** 데이터셋 버전 목록의 출처(`task_keys`)와 지금 시험 설정을 대조합니다. 겹치면 학습을 시작하지 않고 알립니다. 출처가 없는 legacy 데이터셋이면 '호환 확인 불가'로 시작하고, 결과는 자동 채택하지 않고 '채택 대기'로 둡니다. 이 버전들은 지워지지 않으므로(아래 '버전과 채택'), 학습 중에 다른 관리 일이 채택을 바꿔도 학습이 읽는 파일은 그대로입니다.
- 학습 결과는 새 버전 경로에 쓰고, 끝나면 심판이 채택합니다. 학습을 시작한 뒤 그 모델의 채택 표시가 바뀌었으면(예: 복원·초기화. 버전 문자열이 아니라 **채택 gen**으로 비교해 A→B→A도 알아챔), 자동 채택하지 않고 '채택 대기'로 두어 사람이 고릅니다.
- **학습 중 설정 변경 (K5, 결정 가):** 학습은 계속합니다. 시험 TASK 설정 등 학습 관련 설정의 새 버전이 채택되면, 심판은 진행 중·완료된 각 모델의 학습 출처(학습·검증 TASK 키, 같은 그루·촬영일 묶음)와 새 시험 TASK를 대조합니다.
  - 겹치는 모델에는 **'새 시험 기준 오염'** 표시를 붙입니다. 이 모델은 새 시험 설정의 평가·모델 비교에서 빠지고, 자동 채택하지 않고 '채택 대기'로 둡니다.
  - 겹치지 않는 모델은 그대로입니다.
  - 학습 출처에는 시작 때의 시험 설정 버전이 남으므로, 그 버전 기준의 성적은 따로 볼 수 있습니다.
  - 약속 8(고정 시험 제외)은 **학습을 시작할 때 채택된 시험 설정 버전 기준**으로 지키고, 그 뒤 바뀐 시험 설정에 대해서는 위 오염 표시로 다룹니다. 이 뜻을 `AGENTS.md` 약속 8에도 적습니다.

### 관리 일

데이터셋 만들기, 학습 초기화(FORCE_NEW), 학습 복원(23번), 모델 정리(29번), 시험 TASK 바꾸기(33번), 청소(34번)는 '관리 일'입니다.

- 관리 일은 **실행 중인 것이 한 번에 하나**입니다. 대기열은 들어온 순서대로이고, 대기 중인 것은 취소할 수 있습니다 (결정 4).
- 관리 일마다 필요한 실행 환경을 적습니다. 23번 Drive 버전 복원은 Colab Drive 인증이 필요하므로 **Colab 실행기에만** 배정합니다 (결정 3). 정리·청소는 CPU.
- **실행기 대기 (6판 결정):** 맨 앞의 일에 맞는 실행기가 없으면(예: 23번인데 Colab 실행기가 없음) 그 일을 '실행기 대기'로 비켜 두고 다음 관리 일을 진행합니다. 맞는 실행기가 생기면 비켜 둔 일이 다음 차례가 됩니다.
- **실행 ID와 인계 (G4):** 관리 일은 실행 ID(`mgmt_<시각>_<종류>`)로 `arb/locks/mgmt.json`을 받습니다. 실행하는 쪽은 `workers/<S>__<실행ID>.json` 생존 신호와 `arb/mgmt/<실행ID>/steps/` 단계 기록을 남기고, 게시하기 전마다 TASK와 같은 권한 확인을 합니다.
- 관리 일 '확인 필요'의 선택 조건은 TASK와 같고(멈춤 보고, 커널 종료 확인, 15분), 관리 잠금은 '다시 하기'의 새 실행 ID에 바로 넘깁니다. '끝난 것으로 처리'는 그 실행의 버전 파일이 완전하고(목록·해시 일치) 관리 잠금의 decision이 맞을 때만 고를 수 있습니다.
- 새 epoch에서 관리 일·학습 실행이 살아 있으면 같은 실행 ID로 다시 발급하고, 죽었거나 모르면 '확인 필요'로 둡니다 (관리 일 칸은 그동안 막힘, 학습 줄은 그 모델만 막힘).
- 마스터가 띄운 작업 프로세스는 Kaggle·Colab 세션이 끝나면 함께 끝납니다. 세션이 살아 있는데 부모 생존 신호가 3분 넘게 끊기면, 작업 프로세스는 지금 단계를 마치고 다음 게시 전에 권한 확인에서 걸려 멈춥니다.

### 버전과 채택 (J2·J5)

모델·데이터셋·시험 TASK 설정은 모두 **버전 경로 + 채택 표시**로 다룹니다.

| 대상 | 버전 경로 (만든 실행만 씀, 바꾸지 않음) | 채택 표시 (심판만 씀) |
| --- | --- | --- |
| 모델 | `runs/<모델>/v/<실행ID>/` | `runs/<모델>/CURRENT.json` |
| 데이터셋 | `datasets/<이름>/v/<실행ID>/` | `datasets/<이름>/CURRENT.json` |
| 시험 TASK 설정 | `sets/test_tasks/v/<실행ID>/_files.json` | `sets/test_tasks/CURRENT.json` |

- 실행은 버전 경로에 다 쓴 뒤 마지막에 그 안에 목록 파일(`_files.json`: 파일·해시·실행 ID·decision·gen)을 쓰고, 완료를 보고합니다.
- **심판은 관리 잠금(또는 학습 잠금)의 decision·gen·실행 ID가 맞는 완료 보고만 채택**합니다. 채택하면 `CURRENT.json`에 버전·채택 gen·시각을 적습니다. 권한을 잃은 실행이 늦게 목록 파일을 써도 채택되지 않습니다.
- 읽는 쪽(학습 목록, 추론·검증의 모델 선택, 데이터셋 사용, 15번 학습 입력, 시험 TASK 제외)은 `CURRENT.json`이 가리키는 버전만 읽고, 받은 파일의 해시를 목록과 대조합니다.
- **학습 초기화**는 파일을 옮기지 않고 채택 표시만 바꿉니다(빈 시작 또는 지정 버전). **23번 복원**은 새 버전 경로로 복원한 뒤 채택합니다. **29번 정리**는 채택되지 않은 버전에 '정리 대상' 표시만 합니다. 기존 경로를 옮기는 관리 일은 없습니다.
- 실제로 지우는 것은 34번 청소뿐입니다: 채택되지 않았고, 진행 중인 학습·실행이 참조하지 않으며, 정리 대상 표시 뒤 30일이 지난 버전만.
- 지금의 `runs/<모델>/weights/…`처럼 버전 경로가 없는 옛 산출물은 운영 전환 때 한 번 `v/legacy/`로 등록해 채택합니다 (옮기지 않고 목록만 만듦).

## 취합 일 (G4·G11)

- 취합은 CPU 작업 프로세스의 일입니다. 실행 ID로 `arb/locks/aggregate.json`을 받고, 생존 신호를 남깁니다.
- 취합은 **읽기 사본으로 계산하고 자기 상태 파일만 게시**합니다. 지금 취합 함수가 하던 다른 쓰기는 각자 맡을 곳으로 보냅니다: 요청 완료 처리는 요청 소유 실행기, 사라진 TASK 이력은 그 TASK 권한을 가진 경로, 기록 압축은 청소(관리 일).
- 숨김·숨김 해제·새로 고침 요청은 **처음부터 취합 일에 배정**합니다. 취합 일이 반영한 뒤 그 요청의 최종 상태도 씁니다 (`relabel/tracked.json` 작성자를 취합 하나로).
- 취합 전에 최신 `tracked.json`을 받습니다. 게시하는 상태 파일에는 epoch·회차를 적고, 앱은 가장 높은 (epoch, 회차)를 씁니다.
- 새 epoch는 취합을 새 실행 ID로 다시 시작합니다. 같은 입력이면 같은 결과이므로 처음부터 다시 해도 됩니다. 옛 실행은 게시 전 권한 확인에서 멈춥니다.

## 차례

- **TASK마다:** 접수 순서(LC·AA 두 폴더를 합친 순서). 앞 요청이 기다리는 TASK는 뒤 요청이 먼저 잡지 않습니다.
- **예외 (결정 1, G9):** 읽기만 하는 백업·export의 '받는 중'은 TASK 순서를 막지 않고 묶음 자리도 차지하지 않습니다. 대신 결과에 export를 요청한 시각의 CVAT 라벨 버전(TASK `updated_date`)을 기록합니다. 받은 파일을 게시할 때만 그 TASK 잠금을 잡습니다.
- **받는 중 기록 (J1):** 서버에 준비를 요청한 백업·export는 요청·TASK마다 파일 하나(`exports/pending/<요청ID>__<TASK>.json`, `backups/pending/<요청ID>__<TASK>.json`)로 남깁니다. 공용 `pending_exports.csv`·`pending_backups.csv`를 여러 실행기가 다시 쓰지 않습니다. 요약은 취합 일이 만듭니다.
- **사람마다:** 묶음 단위로 돌아가며. 한 요청은 5개 TASK 묶음(`W_CHUNK_TASKS = 5`)씩 받습니다.
- **30분 한도(`W_CHUNK_MIN = 30`):** 새 TASK를 시작하지 않는 부드러운 경계. 진행 중인 TASK는 끝냅니다.
- **묶음이 끝나면:** 실행기가 반납을 보고하고, 심판이 반납을 반영한 뒤에 다음 차례를 정합니다.
- **TASK로 나눌 수 없는 일:** 관리 일은 묶음 없이 하나로 처리합니다.

## 신호 (G3)

- 신호는 매번 새 이름으로 만듭니다. 받는 곳은 마스터 하나입니다. 예외는 깨우기 신호(`wake__…`)로, Keeper가 받습니다 ('CTRL앱' 절).
- 처리는 세 단계입니다 (H2·J4·K1):
  1. **계획:** `arb/signal_plan/<신호ID>.json`에 관측 순번, **논리 대상**(요청 ID, 정지 ID, 확인 대상 TASK와 decision), 신호 종류가 정하는 **효과 목록**을 적습니다. 파일 내용은 적지 않습니다.
  2. **효과:** 효과마다 차례로 처리합니다. 모든 효과는 결과물에 **그 신호 ID를 적어 완료 증거**로 남깁니다 (예: 잠금의 `by_signal`, 복구 요청 `REQ_rcv__<신호ID>`, 요청의 취소 표시 `cancel_signal`).
  3. **완료:** 모든 효과의 결과를 적어 `arb/signal_done/<신호ID>.json`.
- **재시작 때** 완료가 없는 신호는 재시작 인계(다시 발급)를 마친 뒤, 효과마다 이렇게 판단합니다. **gen이 다르다는 것만으로 완료로 보지 않습니다.**

| 효과의 상태 | 처리 |
| --- | --- |
| 그 신호 ID의 완료 증거가 있음 | 반영됨 |
| 증거가 없고, 논리 대상에 지금도 적용할 수 있음 | 지금 상태(현재 epoch·gen·소유자)에 적용 |
| 증거가 없고, 대상이 이미 다른 이유로 끝남 (예: 취소할 요청이 이미 완료) | '무효화됨(이유)'로 기록 |
| 증거가 없고, 대상이 다른 소유자로 옮겨 감 (예: 재배정) | 새 소유자에게 적용 |

- **취소는 요청에 붙는 표시**입니다. 취소 신호의 효과는 요청 접수 기록에 `cancel_signal`을 적는 것이고, 배정을 받은 실행기는 매 TASK 시작 전에 이 표시를 봅니다. 그래서 요청이 재배정돼도 취소가 따라갑니다.
- 완료 기록에는 효과별 결과(반영됨·적용함·무효화됨(이유))를 남깁니다. 무효화된 효과가 있으면 CTRL앱 점검 화면에 보입니다.
- 관측 순번은 계획 파일에 남으므로, 재시작 뒤에도 정지·해제 신호의 처리 순서가 바뀌지 않습니다.
- 처리 순서는 마스터가 목록에서 처음 본 순서(관측 순번)입니다. 해제 신호는 어느 정지 신호를 푸는지 ID로 적습니다. 지금의 `until` 보류, 수동 깨우기, 마스터가 멈출 때 GPU도 멈춤의 의미는 그대로 둡니다.
- GPU 작업자에게 멈추라고 할 때는 마스터가 그 작업자의 배정에 '멈춤'을 적습니다. 마스터가 계획적으로 꺼질 때는 꺼지기 전에 이것을 먼저 씁니다. 새 마스터는 배정 파일을 그대로 이어받습니다 (G10).

## 보고·결과·인계 계약 (8판 보충, b8)

구현 1a 코드 검토(M1~M12)에서 드러난 빈 곳을 판정 계약으로 정합니다. `arbiter.py`가 이 계약을 따릅니다.

### 보고의 필수 식별 (M3)

| 보고 | 필수 항목 | 받아들이는 조건 |
| --- | --- | --- |
| 확정 신청 `confirm` | rid·chunk·job·epoch·gen·decision·session·task | 잠금이 `held`, 모든 항목이 잠금과 같고 epoch가 지금 자격 epoch |
| 끝 보고 `end` | 위 + result | 잠금이 `confirm_approved`, 작업번호(job)·승인 gen까지 같음 |
| 멈춤 보고 `stop` | rid·chunk·epoch·decision·session·task | 소유·decision·epoch가 같음 |
| 확정 없는 끝 `result` | rid·chunk·epoch·gen·decision·session·task·result | 잠금이 `held` |
| 묶음 반납 `release` | assign·rid·chunk·epoch·decision·session | 배정이 `active` |
| 게시 잠금 `publish_lock` | rid·chunk·epoch·decision·session·task | **받는 중(read) 배정**이 지금 epoch로 있고, 그 TASK가 **배정 목록에 있으며**, TASK가 비어 있음 (b9 N4) |
| 산출물 완료 `done_run` | lane·type_·name·run·rid·epoch·gen·decision·session | 그 줄의 실행 잠금이 `running`이고 모두 같음 |
| 산출물 없는 완료 `done_job` | lane·run·rid·epoch·gen·decision·session·result | 위와 같음 |

- 항목이 하나라도 빠지면 거절하고 알립니다. 승인할 때 잠금 gen이 오르므로, 끝 보고는 **승인 뒤 gen**으로 냅니다. 재시작 다시 발급으로 gen이 오르면 실행기는 잠금을 다시 읽어 새 gen으로 다시 냅니다.

### 결과 기록 먼저 (M6)

- TASK·실행이 끝나면 심판은 **결과 기록** `arb/results/<요청ID>__<TASK 또는 run·create>__<작업번호>.json`을 먼저 쓰고, 그다음 잠금을 풉니다.
- 요청의 진행(끝난 TASK)은 별도 파일이 아니라 결과 기록에서 매번 계산합니다. 복구 요청의 결과는 원요청 TASK의 결과로도 셉니다.
- 결과 기록은 있는데 잠금 해제 전에 끊겼으면, 다음 회차가 같은 보고를 다시 보고 잠금을 마저 풉니다.
- **결과 기록은 '판정했다'는 뜻이지 '모든 효과를 마쳤다'는 뜻이 아닙니다 (b9 N1).** 산출물 채택의 결과 기록에는 판정(채택·채택 대기와 이유)과 그때의 **전제**(채택 표시의 채택 gen, 시험 설정 버전)를 함께 남깁니다. 끊긴 뒤 이어 할 때 전제가 바뀌었으면(그사이 FORCE_NEW·다른 채택·시험 설정 변경) 채택 표시를 덮지 않고 '채택 대기(superseded·contaminated)'로 돌립니다. FORCE_NEW의 채택 표시 변경도 같은 규칙입니다.

### 인계 기록 (M8)

- 새 epoch의 다시 발급을 마치면 `arb/handover/<epoch>.json`을 씁니다. 이 기록이 없으면 그 epoch에서는 다른 판정을 하지 않고 인계부터 합니다.
- 첫 회차에 개별 잠금·배정 파일을 못 읽었으면 인계 기록의 `pending`에 남기고, 그 파일이 읽히는 회차에 그 자원만 마저 다시 발급합니다 (b9 N3).
- 보고가 기대는 파일(잠금·결과 기록·채택 표시·버전 목록·배정)을 못 읽은 회차에는 그 보고를 '처리됨'으로 두지 않고 다음 회로 미룹니다. 실행 잠금을 못 읽은 회차에는 그 줄의 배정을 거두거나 새 실행을 잡지 않습니다 (b9 N3).
- 첫 회차에 목록을 못 읽으면('모름') 인계를 미루고, 다음 정상 회차에 합니다.

### 작업 종류별 잠금과 완료 (M10)

| 종류 | 잠금 | 완료 보고 | 실행기가 끊기면 |
| --- | --- | --- | --- |
| TASK 일 (track·shape·auto·복구) | `arb/locks/task/<TASK>.json` (묶음 5개) | `end` / `result` + `release` | 승인 전 회수, 승인 뒤 '확인 필요' |
| 받는 중 일 (백업·export) | 게시할 때만 `publish_lock` | `result` + `release` | 회수 |
| 관리 일 | `arb/locks/mgmt.json` (실행 하나) | 산출물이면 `done_run`(채택), 아니면 `done_job` | '확인 필요' → 사람의 `run_choice` |
| 학습 | `arb/locks/train/<모델>.json` | `done_run` | '확인 필요' → `run_choice` |
| 취합 (숨김·새로 고침) | `arb/locks/aggregate.json` (하나) | `done_job` | 잠금을 풀고 다시 계산 |
| 새 TASK 만들기 | `arb/locks/create/<서버·이름 키>.json` | `done_job`(새 TASK 번호 포함) | '확인 필요' → `run_choice` |

- 실행형 일(관리·학습·취합·만들기)의 배정은 그 실행 잠금이 끝나면 함께 닫습니다. 배정만 쓰고 잠금 전에 끊겼으면 배정을 거두고 다시 차례로 돌립니다 (M5).
- TASK 일은 매 회차 배정과 잠금을 대조해, 빠진 잠금을 같은 decision으로 채웁니다 (M5).
- **사람의 실행 선택 `run_choice`:** TASK의 '확인 필요'와 같은 선택 조건(끊긴 뒤 15분 또는 커널 종료 확인, 관리자 강제)을 따릅니다. '끝난 것으로'는 정상 완료와 **같은 완료 함수**를 거칩니다 — 산출물은 버전 목록이 검증됐을 때(`verified`)만, 채택 판정(채택·채택 대기)까지 하고, 새 TASK 만들기는 사람이 확인한 **TASK 번호**를 받아 만들기 결과로 닫습니다 (b9 N2). '다시 하기'는 잠금을 풀어 새 실행 ID로 다시 배정합니다.
- **FORCE_NEW**는 `done_job`의 `current_change`로 채택 표시만 바꿉니다.

### 실행기 권한 확인의 단계 (M1)

| 단계 | 허용하는 잠금 상태 |
| --- | --- |
| `prepare` (받기·추론·확정 신청) | `held`, `confirm_approved` |
| `recovery_publish`, `cvat_write` | `confirm_approved` + 작업번호 일치 |
| `publish` (받는 중 일의 게시) | `held` + 게시 잠금 |
| 모든 단계 | `quarantine`·`free`·`reserved`는 거절 |

### 그 밖

- **정지 보류 기한 (M11):** 기한(`until`)이 지난 보류는 회차마다 풀고, 기한은 Keeper의 `next_wake_at`에 넣습니다.
- **처리기 진행과 '멈춘 것 같음' (2b-1):** 실행기는 처리기가 일하는 동안 생존 신호에 `busy`(단계·요청·TASK·진행 시각·메모)를 싣습니다. 처리기는 오래 걸리는 일 중간에 `ctx.progress()`를 부릅니다. 진행 시각이 한도(TASK·받기·취합 30분, 관리 일·만들기 1시간, 학습 3시간)를 넘게 멈추면 생존 신호가 와도 그 실행기는 끊긴 것으로 봅니다. 그래서 확정 승인 뒤면 격리('확인 필요'), 실행형이면 '확인 필요'가 되고 `worker_stalled` 알림을 남깁니다. 깨어난 처리기의 쓰기는 권한 확인에서 막힙니다.
- **산출물 최종 검증 (2b-1):** 처리기는 산출물을 버전 경로에 올린 뒤 다시 받아 해시·크기를 확인하고, 모두 맞을 때만 `_files.json`(`verified: true`)을 씁니다. 목록을 쓰기 바로 앞에서 권한을 한 번 더 확인합니다.
- **시험 범위 (2b-1 바탕, 2b-6 연결):** 처리기의 CVAT 쓰기는 `ScopedCvat`를 거칩니다. 시험 실행은 지정 프로젝트의 `REH_` TASK에만 쓰고, 운영 실행은 `REH_` TASK에 쓰지 않습니다. TASK 정보를 못 읽으면 쓰지 않습니다.
- **G 입력 (b8):** G 소유 요청은 수집기 자동 요청 종류만, G 소유 신호는 원래 관리자 신호를 연결한 해제만 받습니다.
- **수집기 자동 요청 (11/12·11/16 결정, 0k·0l):** backup은 TASK가 `_uld`로 올라올 때(원본이 videos/·ULD 기록에 있으면 하지 않음), export는 이름이 검토 단계로 바뀔 때. 수집기는 관측한 사건을 `status/auto_pending.json`(보낼 목록)에 먼저 넣고 스냅숏을 바꿉니다. 요청 파일을 만들 때까지 사건을 잃지 않습니다.
  - **같은 TASK의 사건이 쌓이면 합칩니다 (11/16):** 아직 요청을 만들지 않은 같은 TASK·같은 종류의 사건은 최신 하나로 합쳐 요청 하나에 TASK를 한 번 넣습니다. export는 그때의 최종 상태를 받습니다(CVAT은 지난 상태를 export할 수 없음). 장부에 합친 개수를 남깁니다.
  - **같은 요청을 두 번 만들지 않음:** 만들기 전에 '시도함'을, 만든 뒤 파일 ID를 보낼 목록에 남깁니다. ID가 있으면 이미 만든 것으로 봅니다. ID 없이 '시도함'만 있으면 Drive 검색으로 찾고, 못 찾아도 10분은 다시 만들지 않습니다. 그래도 같은 요청 ID 파일이 둘 생기면 심판은 하나로 접수하고 알림을 남깁니다.
  - 보낼 목록의 형태가 틀리면(시각 칸이 실제 날짜가 아닌 경우 포함) 수집기는 실패로 끝나고 스냅숏을 바꾸지 않습니다. Keeper는 마지막 성공 시각(`last_ok`)이 20분 넘으면 '수집기 멈춤'을 알립니다. 한 번도 성공한 적이 없으면 연속 실패 시작 시각(`fail_since`)부터 셉니다.
  - 장부(`auto_requests.json`)의 TASK별 기록은 더 최신 사건일 때만 바꿉니다. 늦게 발행된 옛 요청은 `history`에만 더합니다 (0m, Z3). '원본 있음으로 건너뜀' 기록도 같은 규칙입니다 (0n, Q4).
  - 사건 시각(`updated`) 비교는 글자가 아니라 실제 시각(숫자)으로 합니다. 소수초·시간대 표기가 달라도 순서가 맞습니다 (0n, Q3).
- **'모름'은 막는 쪽으로 (M8):** 자격 소유자를 못 읽으면 판정하지 않고, 개별 잠금 파일을 못 읽으면 그 TASK의 배정·만료·보고 반영을 미루며, 신청 목록을 못 읽은 회차에는 처리한 보고 목록을 줄이지 않습니다.
- **제출본 (M12):** 프레임 범위와 프레임맵 지문을 필수로 넣고 검증합니다.
- **시험 설정 채택은 두 효과 (b10 P1):** 채택 표시와, 겹치는 모델의 오염 표시입니다. 채택 표시가 이미 반영돼 있어도 오염 표시는 마저 만듭니다. 사람이 시험 설정을 채택할 때도 시험 키를 채택 표시에 넣고 같은 오염 대조를 합니다.
- **완료가 읽는 파일 (b10 P2):** 실행 잠금, 결과 기록, 대상의 채택 표시, 시험 설정 채택 표시(모델일 때), 버전 목록, 그 버전의 플래그. 정상 보고와 사람의 선택(`run_choice`·`adopt_choice`) 모두, 이 가운데 하나라도 못 읽은 회차에는 미룹니다. '없음'과 '못 읽음'을 같은 것으로 다루지 않습니다.
- **사람이 해소한 판정은 되살리지 않음 (b10 P3):** 채택 대기를 사람이 채택·버림으로 처리한 뒤에는, 옛 완료를 이어 처리해도 그 표시를 다시 채택 대기로 돌리지 않고 남은 잠금·배정만 닫습니다.
- **격리된 TASK (1b):** '확인 필요'인 TASK는 같은 요청의 새 묶음으로도 다시 배정하지 않습니다. 사람의 선택을 기다립니다.
- **판정 정본을 못 읽은 회차 (1b):** `arb/` 목록을 못 읽으면 회차 기록도 쓰지 않습니다. 버전 파일 목록을 못 읽으면 보고·신호를 반영하지 않습니다.

## 감시와 재시작 점검

### 누가 멈춤을 알아채는가

모든 핵심 기능은 자기 생존 신호를 남기고, 서로 다른 계정·기계가 서로를 지켜봅니다.

| 멈춘 것 | 표시 | 1차 감시 | 2차 감시 | 조치 |
| --- | --- | --- | --- | --- |
| 판정 루프 | ARBITER 회차가 3분 넘게 그대로 | Keeper | 앱 | 자격 다시 주기·깨우기. 두 번 실패하면 메일 |
| 마스터 프로세스 | `workers/<마스터>.json` 3분 끊김 | Keeper | 앱 | 위와 같음 |
| CPU 작업 프로세스·관리 일·취합 | 실행 ID별 생존 신호 3분 끊김 | 판정 루프 | 앱 | 관리 일은 '확인 필요', 취합은 다시 시작 |
| 실행기 | `workers/<S>.json` 3분 끊김 | 판정 루프 | 앱 (요청이 멈춤) | 확정 전 재배정, 확정 중 '확인 필요' |
| 수집기 (U1) | `status/collector.json` 20분 지남 | Keeper | 앱 | 메일 |
| Keeper (U2) | `jobs/keeper.json` 5분 지남 | 판정 루프 | 앱, Google 트리거 실패 메일 | 앱 위쪽 경고 띠 |
| 마스터와 Keeper 모두 | 모든 시각이 지남 | 앱 (사람) | Google 트리거 실패 메일 | 앱에 '배정기 멈춤 n분, 마지막 시각' |

- 마스터가 쓰는 알림은 `arb/alerts/<ID>.json`에 남기고, Keeper가 메일로 보냅니다.
- CTRL앱이 모든 생존 신호 시각을 한 화면에 보여 줍니다 (LC·AA앱에는 한 줄 요약). 자동 감시가 모두 꺼져도 사람이 화면에서 알 수 있습니다.

### 재시작 점검

새 마스터가 자격을 받은 첫 회에, 판정보다 먼저 아래를 대조합니다. 결과는 `arb/recovery/<epoch>.json`에 남기고 앱에 '재시작 점검: 이상 n건'으로 보여 줍니다.

| 대조 | 이상일 때 |
| --- | --- |
| 진행 중 요청마다 살아 있는 실행기·잠금이 있는가 | 확정 전이면 재배정, 아니면 '확인 필요' |
| 확정 승인마다 확정 끝이 있는가 | 실행기가 살아 있으면 새 epoch로 다시 발급, 죽었으면 '확인 필요'. 복구 자료가 있는지도 확인 |
| 잠금마다 assign과 decision ID가 맞는가 | 새 epoch로 다시 발급하거나 회수 |
| 신호마다 완료 파일이 있는가 | 다시 발급을 마친 뒤, 효과마다 완료 증거를 보고 '신호' 절의 표대로 처리하고 완료 |
| 관리 일·취합 실행 ID가 살아 있는가 | 관리 일·학습은 다시 발급 또는 '확인 필요'(버전 목록 유무 표시), 취합은 다시 시작 |
| 받는 중인 백업·export, 남은 묶음, 처리 안 된 정지 | 이어받아 대기열에 둠 |
| 마지막 회차 시각과 끊긴 시간 | 보고서에 적음 |

### 정기 점검

같은 대조를 10분마다 가볍게 실행합니다 (판정 루프 9단계). 마스터는 살아 있는데 실행기 하나가 조용히 죽었거나, 파일 하나를 못 읽어 '모름'이 이어지는 경우를 찾습니다. 정기 점검에서 더 보는 것:

- **멈춘 것 같음:** 생존 신호는 오는데 단계 기록이 일정 시간(TASK 30분, 관리 일은 종류별 한도) 바뀌지 않는 실행.
- **승인 없는 쓰기:** 위 '확인 필요' 절의 찾아내기.
- **실행기 대기:** Colab 전용 일처럼 맞는 실행기가 없어 기다리는 것은 장애가 아니라 '실행기 필요'로 따로 표시.

### 생존 신호와 진행 (8판 보충, b12)

- 생존 신호는 일하는 줄과 다른 스레드가 보냅니다 (Q1). 그래서 처리기가 무한히 기다려도 '살아 있음'으로 보입니다. **생존 신호를 끊는 것으로 해결하지 않습니다** — 자동 재배정이 옛 쓰기와 겹칠 수 있기 때문입니다.
- 2단계 필수: 처리기는 단계마다 **진행 시각**을 단계 기록에 남기고, 단계별 **시간 한도**(CVAT 호출, prepare·fetch·run, 외부 프로세스)를 둡니다. 한도를 넘으면 실행기가 스스로 멈춤을 보고하고, 보고도 없이 진행 시각만 멈추면 정기 점검의 '멈춘 것 같음'이 '확인 필요'로 넘겨 사람이 고릅니다.
- 생존 신호 파일은 생존 신호 스레드 하나만 씁니다. 끝날 때의 '끝남'도 그 스레드가 마지막으로 씁니다 (R7).

### 산출물 목록 (8판 보충, b12)

- 실행형 일(관리 일·학습)의 버전 경로 산출물은 **모든 파일을 쓰고 다시 확인한 뒤 마지막에** `_files.json`(파일별 해시, `verified`, 실행 ID·decision·gen)을 확정합니다. 확정 뒤에는 바꾸지 않습니다.
- 심판은 `_files.json`이 없거나 비었거나 `verified`가 없으면 채택하지 않습니다. 2단계 연결 시험에 파일 누락·해시 불일치·다른 실행 ID·확정 뒤 변조·권한 상실 중단을 넣습니다.

### 보호 모드 (8판 보충, 11/15 결정)

판정 파일(`arb/`의 접수·결과·배정·잠금·계획·완료·보류·표시·인계, 그리고 `CURRENT.json`)은 심판만 씁니다. 그래서 이 파일이 믿을 수 없게 되었다면 사람이 손댔거나 프로그램 결함이 있다는 뜻입니다. 칸마다 따로 처리하지 않고 하나의 규칙으로 막습니다.

- **들어가는 조건:** 판정 파일이 하나라도 다음과 같을 때입니다. 회차를 시작할 때 확인합니다.
  - 객체가 아님
  - 형태 표(`JUDGEMENT`)에 맞지 않음
  - 종류별 필수 칸이 없음 (계획의 `seq`·`effects`, 배정의 `rid`·`tasks`·`session`·`state`·`decision`·`epoch` 등)
  - 상태 값을 모름
  - 세션 지문이 없거나, 미래 epoch이거나, 같은 epoch의 다른 세션 것임
  - 끝나지 않은 신호 계획이 신호와 맞지 않음 (0k, b17 X1): `sid`·종류·대상이 다르거나, 효과 목록이 신호에서 다시 계산한 것과 다름 (일부 빠짐·겹침·바뀜·순서). 효과 목록은 신호만으로 정해지므로 다시 계산할 수 있습니다
  - 계획의 요청자가 신호 파일 소유 계정에서 다시 계산한 사람과 다름, 또는 `admin`이 참·거짓이 아님 (0l, b18 Y1)
- **관리자 권한 (0l, b18 Y1):** 신호를 처리할 때 관리자 권한(강제 해제 등)은 계획에 적힌 `admin`을 쓰지 않고, 지금 신호 소유자의 사람 목록 권한으로 매번 정합니다. 계획 뒤 관리자에서 내려가면 강제 해제는 무효입니다.
- **계획을 이어 할 때의 신원 (11/16 결정, 0m, b19 Z1):** 신호 소유자를 매 회차 다시 확인합니다. G가 낸 해제는 연결된 원래 신호의 소유자를 봅니다.
  - **모름** (소유 계정을 못 읽음, G 해제의 원래 신호 파일을 못 읽음·같은 이름 여럿): 끝내지 않고 다음 회차로 미룹니다. 새 신호를 처음 계획할 때도 같습니다 (0n, b20 Q2). 원래 신호가 정말 없으면 거절합니다.
  - **권한 철회** (사용 중지·권한 없음·등록 없음): 아직 적용하지 않은 효과는 `invalid:revoked:<이유>`로 거절하고 끝냅니다. 이미 적용한 효과는 그대로 둡니다.
  - **허용**: 진행합니다.
- **같은 이름 파일 여럿 (11/16 결정, 0m, b19 Z4):** 마스터가 Drive 목록을 읽을 때 한 폴더에 같은 경로가 둘 이상 나오면, 그 파일은 '모름'으로 두고 `duplicate_path` 알림을 남깁니다. 관리자가 하나를 지울 때까지 처리하지 않습니다. rclone이 같은 이름 파일 중 어느 것을 읽고 쓰는지 보장되지 않기 때문입니다.
  - **판정 보류 (11/16 결정 A, 0o, b21):** 읽지 못한 것이 하나라도 있으면(목록 실패·파일 읽기 실패·같은 이름 여럿) 그 회차는 **아무 판정도 하지 않습니다.** 회차 기록(`ARBITER.json`의 `hold_on`·`hold_on_since`)과 알림만 씁니다. 다음 회차에 다 읽히면 이어서 합니다. 이 규칙이 0n까지의 '모름' 하나하나에 대한 처리(보류 모름·계획 모름·인계 모름·N3의 미룬 자원 인계)를 대신합니다. 예외: 사람 목록이 오래된 것(`config`)은 따로(하던 일만 마무리, Q3).
    - 판정 보류 중 `wake`: 할 수 있는 일 0, GPU 필요 0, `holds`에 `(모름)`. Keeper는 심판이 살아 있다고 보므로 새 마스터를 깨우지 않습니다. 마스터는 이 회차를 빠짐없는 회차로 세지 않으므로 밤에 끝내지 않습니다.
    - 30분이 넘으면 `hold_on_long` 알림 → Keeper가 메일·푸시. CTRL앱 위쪽에 '판정 보류' 띠(읽지 못한 것, 같은 이름 파일 안내).
    - 문법은 맞는데 객체가 아닌 JSON은 '모름'이 아니라 그대로 넘깁니다. 바깥 입력이면 형태 검사로 거절, 판정 파일이면 보호 모드입니다. 고쳐지지 않는 잘못된 바깥 파일 하나가 전체를 멈추지 않게 하기 위해서입니다.
    - **실행기도 같은 규칙 (0p, b22 R1):** 읽지 못한 것이 하나라도 있으면 그 차례는 일하지 않고 기다립니다. 객체가 아닌 판정 파일·자격 파일은 '모름'으로 하고 읽는 목록에서 뺍니다(다른 코드가 건드리지 못하게). 객체가 아닌 바깥 입력(요청 등)은 그냥 뺍니다 — 심판이 거절하므로 실행기가 멈출 이유가 아닙니다.
    - **GPU 기동 (0p, b22 R2):** 마스터는 이번 회차에 회차 기록을 실제로 썼을 때만 그 요약으로 GPU 작업자를 켭니다. `arb/` 목록을 못 읽어 회차 기록을 쓰지 않은 회차에는 지난 요약을 쓰지 않습니다.
    - 읽지 못한 경로에 쓰지 않는 규칙(`View.put`, 0n)은 보조 안전장치로 남깁니다.
- **하는 일:** 회차 기록(`ARBITER.json`의 `protect`)과 알림만 씁니다. 접수·배정·보고 반영·만료·신호 처리·GPU 기동은 하지 않습니다. Keeper는 심판이 살아 있다고 보므로 새 마스터를 깨우지 않습니다.
- **알림 (11/15 결정):** Keeper가 들어갈 때 메일과 휴대폰 푸시(ntfy, 최고 우선순위)를 보내고, 끝날 때도 보냅니다. CTRL·LC·AA앱은 위쪽에 보호 모드 띠를 보입니다.
  - 정상에서 보호로 바뀔 때마다 새 사건으로 알립니다. 같은 손상으로 다시 들어가도 알립니다. 같은 보호 구간 안에서 같은 이유는 한 번만 알립니다 (0k, X4).
  - 보내지 못한 메일·푸시는 `keeper.json`의 보낼 목록(`outbox`)에 남겨 1분마다 다시 보냅니다(30번까지). 목록에는 ntfy 주제 이름과 메일 주소를 넣지 않습니다.
  - 보낼 수 없는 동안 보호 모드가 여러 번 바뀌면 메일·푸시 각각 '지금 상태' 하나만 남기고, 그사이 바뀐 횟수를 본문에 적습니다 (0m).
  - 보낼 목록은 50개까지입니다. 보호 모드 들어감·끝남 알림은 상한과 횟수에 상관없이 남깁니다. 넘쳐서 버린 일반 알림은 '보냄' 이력에서 지워, 상태가 그대로면 다시 알립니다. 버린 개수는 요약 메일 한 통으로 알립니다 (0l, Y6).
  - `keeper.json`을 읽지 못하면 보낸 알림 이력을 모르므로, 지금 보이는 상태 알림은 다시 보내지 않고 보호 모드만 한 번 더 알립니다. 그 사실을 메일 한 통으로 알립니다.
- **실행기:** 하던 단계까지 하고 보고를 남긴 채 기다립니다. 권한 확인이 손상된 잠금을 읽으면 `lock_untrusted`로 멈춥니다.
- **끝나는 조건:** 관리자가 파일을 바로잡으면 다음 회차부터 정상으로 돕니다 (배포 계획의 '관리자 복구 절차').
- 읽기 실패는 보호 모드가 아니라 지금처럼 '모름'으로 다룹니다. 바깥 입력(보고·신호·요청·실행기·산출물 목록)이 틀리면 그 파일만 거절합니다.
- 회차 기록(`ARBITER.json`)만 예외입니다. 손상되면 빈 기록으로 보고 다시 씁니다. 처리한 보고 목록을 잃으므로 보고를 다시 확인하는데, 이는 식별 대조로 중복 효과가 나지 않습니다.

### 자동으로 알 수 없는 것

- 마스터와 Keeper가 함께 멈추고 Apps Script 트리거 자체가 지워진 경우에는 메일도 오지 않습니다. 이때는 CTRL앱을 여는 사람만 알 수 있습니다.
- 끊긴 실행기가 CVAT에 실제로 무엇을 넣었는지는 알 수 없습니다. 그래서 '확인 필요'로 두고, 복구 자료와 CVAT 현재 상태를 나란히 보여 사람이 고릅니다. 복구 자료가 CVAT 쓰기 전에 게시되어 있다는 것(실행기 5단계)이 이 비교의 전제입니다.

## 새 TASK 만들기 (16·17번, J7)

새 TASK를 만드는 일(영상·이미지로 만들기, 백업에서 새 TASK로 복원)은 호출 결과로 TASK 번호가 생기므로, 기존 TASK 잠금 절차를 그대로 쓸 수 없습니다.

1. **같은 이름 만들기는 하나씩:** 같은 CVAT 서버·같은 계정에서 같은 이름의 TASK 만들기는 심판이 한 번에 하나만 허가합니다 (`arb/locks/create/<이름 해시>.json`).
2. **의도 기록:** 만들기마다 의도를 따로 기록합니다: `recovery/create/<요청ID>/<작업번호>/intent.json` (만들 이름, 원본 파일과 해시, 예상 프레임 수, 라벨, 시각, 실행기, decision). 한 요청에 만들기가 여럿이면 작업번호로 나눕니다.
3. **빈 TASK 먼저:** TASK를 먼저 만들고(빈 TASK) 응답의 **번호를 바로 기록**한 뒤, 미디어를 올립니다. 번호를 모르는 구간은 TASK 만들기 호출 하나로 줄어듭니다. 이름을 바꾸는 단계(16번의 꼬리표)도 번호 기록 뒤에 합니다.
4. **응답을 못 받았거나 번호 기록 전에 끊기면 다시 만들지 않습니다.** 복구 때 CVAT에서 '의도 시각 뒤에 우리 계정이 만든 같은 이름(또는 꼬리표 붙은 이름)의 TASK'를 찾습니다.
   - 후보가 하나이고, 서버 작업 ID가 의도와 맞으면 그 TASK로 이어 갑니다.
   - 후보가 하나이고 미디어가 올라가 있으면, 원본 해시·프레임 수가 의도와 맞을 때만 이어 갑니다.
   - **미디어가 없는 빈 TASK는 서버 작업 ID 같은 증거가 없으면 하나뿐이어도 이어받지 않고 '확인 필요'**로 둡니다. ULD앱과 사람의 CVAT 웹 생성은 같은 이름 잠금 밖이라, 이름만으로는 우리 것이라고 할 수 없습니다 (L3).
   - 기존 16번(백업에서 새 TASK)·17번이 빈 TASK 먼저 만들기를 지원하지 않으면 그 작업은 한 번 호출로 두고, 응답 유실은 위 규칙대로 확인 필요로 다룹니다 (다른 경로로 우회하지 않음).
   - 후보가 없으면 서버 작업이 끝났는지 확인할 수 있을 때만 다시 만들기를 허용합니다.
   - 둘 이상이거나 맞는지 확인이 안 되면 '확인 필요'로 둡니다. 앱은 TASK를 지우지 않으므로, 중복이 생겼으면 사람이 CVAT에서 처리합니다.
- 기존 TASK의 라벨을 백업으로 되돌리는 일(TASK 잠금 사용)과 백업에서 **새 TASK로 복원**하는 일(이 절차)을 구별합니다.
- TASK 이름 규칙은 바꾸지 않습니다.

## CTRL앱 (시스템 감시)

시스템 전체를 보는 새 앱입니다. LC·AA앱은 요청 처리 상태를 보고, CTRL앱은 시스템 상태를 봅니다.

| 화면 | 내용 |
| --- | --- |
| 감시 | 판정 루프·마스터·작업 프로세스·실행기·수집기·Keeper의 마지막 생존 시각과 상태 ('감시와 재시작 점검'의 표) |
| 점검 | 재시작 점검 보고서, 정기 점검의 '모름'·이상 목록, 알림 |
| 관리 일 | 관리 일 대기열·진행 중 실행 ID, '확인 필요' 목록 |
| 제어 | 마스터 깨우기, 정지 보류 상태, 정지·해제 |

### 마스터 깨우기 (비상 버튼)

| 단계 | 하는 곳 | 내용 |
| --- | --- | --- |
| 1. 버튼 | CTRL앱 | 마지막 생존 시각·정지 보류 여부를 함께 보여 줌. 심판이 살아 있으면 버튼을 막음 |
| 2. 1차 권한 확인 | CTRL앱 | `people.json`에서 깨우기 권한(`wake`)이 있는 사람인지. 확인 창 |
| 3. 신호 | CTRL앱 | `jobs/signals/wake__<M>__<순번>.json` |
| 4. 2차 권한 확인 | Keeper (1분 안) | ① 신호 파일의 **Drive 소유 계정**이 `people.json`의 그 사람 계정인지 ② 최신 `people.json`에서 그 사람이 `active`이고 `wake` 권한이 있는지 (목록을 못 읽으면 거절) ③ 신호가 만들어진 뒤 수정되지 않았고 10분이 지나지 않았는지 ④ 살아 있는 심판이 정말 없는지 ⑤ 최근 10분 안에 깨운 적이 없는지 ⑥ 정지 보류 판정 (아래) |
| 5. 깨우기 | Keeper | 시도 ID를 만들어 `jobs/wake_done/<신호ID>.json`에 '처리 중(시도 ID·단계)'을 먼저 적은 뒤, Kaggle API로 `deploy/`의 승인된 마스터 노트북을 push. 단계마다 기록, 끝나면 결과를 적음 |
| 6. 표시 | CTRL앱 | 깨우기 접수됨 → Keeper 확인됨 → 기동 요청 보냄 → 마스터 살아남, 또는 거절 사유 |

- 깨우기 신호는 마스터가 꺼져 있을 때 쓰는 것이므로 **Keeper가 받는 유일한 신호**입니다. 처리 기록은 `jobs/wake_done/`에 따로 둡니다.
- **정지 보류 판정 (H4):** Keeper의 모든 깨우기(주간 상시, 할 일 깨우기, 버튼)는 같은 판정 하나를 거칩니다. 처리 안 된 정지가 있으면 깨우지 않습니다. 예외는 하나뿐입니다: 관리자의 **'보류 해제하고 깨우기'**가 2차 확인을 통과하고, 그 신호에 적힌 정지 ID가 지금 걸린 정지와 정확히 같을 때. 이때 Keeper는 해제 신호를 만들고 깨웁니다. 해제 신호가 있다는 것만으로는 깨우지 않습니다.
- **Keeper 중간 장애 (J8):** Keeper가 '처리 중'인 깨우기를 다음 회에 발견하면, 먼저 심판이 살아 있는지와 Kaggle 커널 상태(대기·실행 중)를 확인합니다. 살아 있거나 실행 중이면 '완료'로 적습니다. 둘 다 아니고 push가 접수됐는지 모르면 '기동 결과 모름'으로 두고, 시도 뒤 10분이 지나면 **한 번만** 다시 push합니다. 그래도 안 되면 '실패'로 적고 알립니다.
- '보류 해제하고 깨우기'는 동작 ID 하나로 묶습니다. 해제 신호와 깨우기는 같은 동작 ID의 두 단계이고, 둘 다 끝나야 완료입니다. 재시작 때 남은 단계만 이어 합니다.
- '보류 해제하고 깨우기'는 `people.json`의 역할이 `admin`이고 `release` 권한이 있는 사람만 씁니다. 지금의 `wakeCpuMasterNow`(정지를 지우고 깨움)는 이 동작으로 옮깁니다.

### 관리자 인증

- `people.json`의 관리자 Google 계정은 **2단계 인증을 켜 둡니다.** Keeper의 2차 확인이 Drive 소유 계정에 기대므로, 이 계정이 안전해야 합니다.
- 동작별 일회용 코드(TOTP)는 넣지 않습니다 (11/14 결정). 관리자가 늘어나면 다시 논의합니다.

### 실행 코드의 신뢰 경계 (H6·J10)

- 실행되는 코드는 모두 **관리자만 편집할 수 있는 `deploy/` 폴더**에서 나옵니다: 마스터 노트북과 실행 설정(kernel metadata), `scripts/`, `notebook_cells.json`. 다른 계정은 보기 권한만 줍니다.
- **한 방향 검증 사슬 (K2):**

| 단계 | 무엇을 | 무엇으로 검증 |
| --- | --- | --- |
| 1 | 마스터 노트북 (뿌리) | Keeper Script Properties의 `MASTER_NB_SHA256` |
| 2 | 배포 목록 `deploy/manifest.json` | 마스터 노트북 안에 고정한 목록 해시 |
| 3 | 목록에 든 파일: `scripts/**`, `notebook_cells.json`, GPU 작업자 노트북과 실행 설정, CPU 마스터 실행 설정 | 목록의 파일별 해시 |

  - 목록에는 **마스터 노트북과 목록 자신을 넣지 않습니다.** 그래서 순환이 없습니다.
  - 배포 순서: ① scripts 등 파일 확정 → ② 목록 만들기 → ③ 목록 해시를 마스터 노트북에 넣기 → ④ 마스터 노트북 해시를 Keeper에 등록. Colab 노트북(0번·30번 셀이 든 사람용 사본)에는 ③과 같은 목록 해시를 넣습니다.
- 마스터·CPU 작업 프로세스·GPU 작업자·0번·30번 셀은 scripts를 import하거나, `load_script`로 불러오거나, subprocess로 실행하거나, 셀 코드를 실행하기 **전에** 파일 해시를 목록과 대조하고, **검증한 바로 그 바이트**를 실행합니다. 하나라도 다르면 실행하지 않고 알립니다.
- 마스터가 GPU 작업자를 켤 때(`start_gpu_worker_if_needed`)는 `deploy/`의 검증된 GPU 노트북과 실행 설정만 씁니다.
- 새로 배포할 때는 관리자가 위 순서대로 함께 바꿉니다.
- Keeper는 신호에서 노트북 경로·kernel slug·실행 옵션을 받지 않습니다. Keeper 프로젝트의 편집자는 관리자 계정 하나로 둡니다. 오류 기록·메일에 Kaggle 응답 원문을 넣지 않습니다.

## 운영 전환

1. **막기 → 비우기 → 대장 → 사본** (b12 R4, 자세한 순서는 `DEPLOY_PLAN_v4.33.md` 6절): 앱의 새 요청 제출을 막고, 옛 자동 배정(트리거)을 끄고, 진행 중인 일과 CVAT 서버 가져오기 작업이 끝날 때까지 기다린 뒤 세션을 끕니다. 요청마다 실제 처리 여부를 전환 대장에 적습니다. 끝나지 않은 옛 요청은 이름을 '전환 확인 필요'(`__transition`)로 바꾸고, 새 심판은 상태가 '대기'(`pending`)인 요청만 접수합니다.
2. **계정 전환:** Kaggle 노트북(마스터·작업 프로세스·GPU 작업자)은 K Kaggle에 있고 `RCLONE_CONF`(A0 토큰)를 그대로 씁니다. K의 Kaggle 보안 비밀에 `KAGGLE_USERNAME`·`KAGGLE_KEY`를 넣습니다. Apps Script(수집기·Keeper)를 G 계정에서 두 프로젝트로 새로 만들고 Script Properties를 넣습니다 (수집기: CVAT 토큰, Keeper: K의 Kaggle 키·`MASTER_NB_SHA256`). K Kaggle 계정의 옛 Apps Script는 **이 단계에서** 트리거를 끄고 Script Properties의 CVAT 토큰을 지웁니다. `eggplant_admin/` 폴더를 만들고 `config/accounts.json`을 씁니다.
3. **배포:** `deploy/`에 파일을 올리고 배포 목록·노트북 고정 해시·Keeper 해시를 '실행 코드의 신뢰 경계' 순서대로 맞춥니다. `config/min_version.json`을 올립니다. 버전은 숫자로 비교합니다.
4. **옛 산출물 등록:** 모델·데이터셋·시험 TASK 설정의 지금 파일을 옮기지 않고 `v/legacy/` 목록으로 등록하고 `CURRENT.json`이 가리키게 합니다. 이 등록은 새 심판이 자격을 받은 첫 회에 합니다 (세션 지문 표시가 붙도록). 옛 `config/test_tasks.json`은 `sets/test_tasks/v/legacy/`로 등록합니다. 목록은 버전 경로 밖의 옛 파일을 가리킬 수 있고, 청소는 legacy 목록의 원본을 지우지 않습니다. 지금의 공용 `pending_*.csv`의 행은 요청별 파일로 옮깁니다.
5. 마스터를 켜 자격을 받습니다. 첫 회 재시작 점검이 옛 세션의 일을 정리합니다.
6. 작업자를 켭니다. 최소 버전보다 낮은 세션과 최소 버전 파일을 못 읽은 세션은 공유 쓰기를 하지 않습니다.

## 계정 역할

| 계정 | 하는 일 | CVAT 토큰 | 주기 |
| --- | --- | --- | --- |
| U1 수집기 (`Collector.gs` + `Uld.gs`, G 계정) | CVAT 목록·준비 상태, 사라진 TASK, 자동 요청 | 있음 | 10분 |
| U2 Keeper (`Keeper.gs`, G 계정 — 수집기와 다른 프로젝트) | 심판 자격, 깨우기(Kaggle push), 깨우기 신호 처리, 감시, 알림 메일, 자기 생존 신호 | 없음 | 1분 |

Keeper의 깨우기 조건 (살아 있는 심판이 없을 때, G10):

- **주간 상시 (지금과 같음):** 08:00~19:00에는 할 일이 없어도 마스터를 켜 둡니다.
- 마지막 `arb/ARBITER.json`의 **`next_wake_at`이 현재 시각보다 이름** (K4). 심판은 회차마다 다음 깨울 시각을 계산해 적습니다: 받는 중의 다음 확인 시각, 야간 승인 일의 시작 시각, 다음 아침 08:00 중 가장 이른 것. 지금 바로 할 일이 있으면 지금 시각입니다.
- 마지막 `arb/ARBITER.json`의 **지금 실행할 수 있는 일 수**가 0보다 큼. 심판이 회차마다 계산합니다: 대기 요청 중 실행 가능한 것(밤에는 야간 승인된 것만), 받는 중이고 다음 확인 시각이 지난 것, 남은 묶음, 취합 필요, 관리 일·학습 대기 중 맞는 실행기가 있는 것
- 심판이 아직 보지 못한 새 요청이 있음: 심판은 회차마다 **목록을 읽기 시작한 시각**(`observed_from`)과 그때 본 요청 ID를 적고, Keeper는 그 목록에 없는 '대기 중' 요청이 있으면 깨웁니다 (K4). 밤에는 이것으로 깨우지 않고 아침 08:00에 처리하며, 앱에 '아침에 처리됨'으로 표시합니다
- 실행기가 새로 켜짐(`workers/`에 새 세션): 비켜 둔 관리 일·학습에 맞는 실행기가 생긴 경우
- 처리 안 된 신호: 일반 신호는 `arb/signal_done/`, 깨우기 신호는 `jobs/wake_done/`과 비교 (J3). 거절·실패로 끝난 것도 '처리됨'입니다. 밤에는 복구·제어 신호(확인 결과, 정지·해제, 취소)만 깨울 근거입니다
- 모든 깨우기는 'CTRL앱' 절의 **정지 보류 판정**을 거칩니다.

Keeper는 한 회 2초 이내를 목표로 실측합니다(깨우는 회차는 예외). 배정·야간 승인·GPU 큐 쓰기·`dispatcher.json`은 Apps Script에서 뺍니다.

- **깨우는 방법:** Keeper가 Kaggle API로 마스터 노트북을 직접 push합니다. GitHub Actions 경로(`triggerGhDispatch_`, `GITHUB_TOKEN`, `GITHUB_REPO`)는 없앱니다.
- **Script Properties (U2):** `KAGGLE_USERNAME`, `KAGGLE_KEY`, `MASTER_NB_SHA256`. 코드·Drive·로그·대화에 쓰지 않고, 웹앱으로 배포하지 않습니다. `RCLONE_CONF`는 Keeper에 넣지 않습니다(Apps Script는 Drive를 직접 씀).
- Kaggle API 키는 계정마다 하나라서, 새로 만들면 Kaggle 보안 비밀의 기존 키가 무효가 됩니다. 지금 키를 그대로 Keeper에도 넣습니다. 나중에 키를 바꾸면 두 곳을 함께 바꿉니다.

## 사람 목록 (`config/people.json`)

- 처음에는 M1(재웅님, 역할 `admin`, 권한 `request`·`wake`·`release`)만 넣습니다. 칸: 번호, 표시 이름, Google 계정, 역할, 권한, 상태(`active`/`stopped`).
- 마스터와 Keeper가 10분마다 다시 읽으므로 사람을 추가할 때 재시작이 필요 없습니다.
- 목록에 없거나 `stopped`인 사람의 세션은 분석 모드로 읽기만 합니다. 요청·신호는 'people.json 등록 필요'로 거절합니다.
- 번호는 다시 쓰지 않습니다. 사람이 빠지면 지우지 않고 `stopped`로 둡니다.

### b24 반영 (0z, 11/17 결정 포함)

- 가져오기는 접수와 완료 확인을 나눔. 되돌리기는 접수 자체의 분명한 거절이나 그 작업의 failed를 확인했을 때만, 그 밖은 '확인 필요'

- 학습은 별도 프로세스 묶음, 실행기가 진행·권한을 지켜보고 잃으면 묶음 전체를 끝냄. 학습 프로세스는 자기 작업 폴더에만 쓰고 공유 폴더 게시는 실행기가 실행마다 다른 버전 경로로
- 모델 선택 목록은 채택된 모델 버전에서 계산 (웹·relabel 공통)

### b26 반영 (0z2)·2c 결정 (11/17)

### b28 반영 (0z6)·결정 (11/17)

- **취소 (D10, 결정):** 등록된 사람이면 누가 등록한 요청이든 취소할 수 있음 (지금 심판 그대로). 미등록 계정은 거절
