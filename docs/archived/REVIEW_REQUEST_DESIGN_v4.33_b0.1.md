# v4.33 설계 검토 요청 — 경합 통제 설계표를 v4.32.0 코드와 대조

이번에는 코드가 아니라 설계를 검토합니다. 대상은 `docs/DESIGN_v4.33.md`이고, 대조할 코드는 저장소의 v4.32.0입니다.

**코드·노트북·시험은 고치지 마세요.** 결과는 `REVIEW_RESULT.md`에 써 주세요. 발견은 D1부터 번호를 붙이고, 형식은 지난 검토와 같습니다(번호·심각도·관련 항목·위치·무엇이 문제인가·일어나는 조건·확신·제안).

## 배경

v4.32.0 검토(S1~S6)에서 공유 파일을 여러 곳이 쓰는 경로가 계속 새로 나왔습니다. 이번 설계는 다음 방식으로 이 문제를 한 번에 다루려 합니다.
- 경합 순간을 나누고, 최소 단위(요청·TASK·앱 상태)마다 쓰는 주체를 하나로 정합니다.
- 결정은 Apps Script 심판 한 곳이 내리고, 세대 번호(gen)로 확인합니다.
- 파일은 지우지 않고 지움 표시만 남깁니다.

운영 전제는 이렇습니다. 사람(M) 여럿, Google 계정(U) 여럿, 실행 세션(S) 여럿이 동시에 일하고, 이 상황은 피할 수 없습니다.

## 검토 질문

1. **빠진 쓰기 경로:** '공유 파일별 쓰는 주체' 표에 없는 곳에서 그 파일을 쓰는 코드가 있습니까? 표에 없는 공유 파일도 있습니까? 아래 경로를 모두 포함해 봐 주세요.
   - 노트북 0~34번 셀
   - `drive/scripts/*.py`
   - `drive/notebooks/kaggle_cpu_master.py`
   - `apps_script/Code.gs`
   - Kaggle 자동 동기화(`drive_sync_now`·`drive_push`)
2. **경합 순간의 빈틈:** C1~C10에 들지 않는 경합 순간이 코드에 있습니까? 특히 사람이 셀을 직접 실행하는 경우, CVAT 쪽 상태(TASK 이름·라벨)가 경합하는 경우, 학습·데이터셋 폴더를 봐 주세요.
3. **확정 단계와 세대 규칙:** 'TASK별 단계와 결과'의 1~6단계와 취소 경계를 실제 코드 순서와 맞춰 봐 주세요.
   - 실제 순서는 30번 셀 `_rl_shape_one`·`_rl_track_one`·`_rl_upload_one`, 5·6·10번 셀에 있습니다.
   - 준비 단계로 분류했는데 실제로는 CVAT나 공유 파일을 바꾸는 곳이 있습니까?
   - 세대 확인 없이 확정 쓰기가 일어날 수 있는 지점이 있습니까?
4. **옮길 때 깨지는 것:** v4.32.0의 장치를 심판 배정 확인으로 바꿀 때 기존 약속이나 시험이 깨지는 곳을 짚어 주세요. 바뀌는 장치는 스스로 맡는 임대(`lease_should_take`·`_own_state`·`lease_tick`), 받은 뒤 2초 확인(`_rl_claim`·`_lc_claim`·마스터 `claim`), `request_owned`·`may_adopt`입니다. 기존 약속은 `AGENTS.md` 3장 1~9번입니다.
5. **지움 표시:** 지금 코드에서 Drive 파일을 지우는 모든 곳을 찾아 주세요. rclone `deletefile`·`delete`·`sync`, `os.remove`·`unlink`, Apps Script `setTrashed`가 대상입니다. 설계표의 '바꿀 방법'으로 덮이지 않는 곳이 있으면 짚어 주세요.
6. **심판의 무게:** 지금 `Code.gs`의 `dispatch_`가 1분마다 하는 일을 기준으로, 심판이 한 번에 읽어야 할 파일 수와 호출 수를 대략 세어 주세요. 하루 90분 한도에 대한 위험을 판단하는 데 쓰겠습니다.
