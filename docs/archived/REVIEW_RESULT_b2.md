### G9 — waiting 잠금 해제와 TASK 접수 순서 보장이 충돌함

| 번호 | G9 |

## 4. 확정·재시작 순서에서 추가로 명시할 조건

- **신청 식별:** `locks/ask/<S>__<자원>.json`은 같은 세션이 다음 요청에도 재사용한다. 신청·승인·끝 보고에 요청 ID·묶음 ID·작업 번호·epoch·gen·decision ID를 넣고, 이전 작업의 끝/승인이 다음 작업에 적용되지 않게 해야 한다.
- **모름의 전파:** 개별 TASK 파일이 아니라 자격·요청 목록·생존 신호를 못 읽었으면 그 자료에 의존하는 모든 자원의 새 승인/회수를 보류해야 한다. 구소유자가 없다고 추정해 재배정하지 않는다.
- **부분 게시:** assign과 lock의 decision ID 일치는 필요하다. 여기에 현재 epoch·실행기 S·TASK 집합·gen 일치까지 검사하고, 묶음 일부 게시 실패 시 어떤 TASK부터 실행할 수 있는지 정해야 한다.
- **재시작:** ‘이전 epoch를 그대로 이어받음’과 ‘현재 epoch만 따름’ 사이에 정본 재발급 단계가 필요하다. 새 심판이 구소유자·진행 상태를 보존한 채 새 epoch로 어떤 허가를 재확인할지 명시한다. 구epoch의 늦은 파일이 정본 경로를 덮으면 독자는 거절할 수 있지만 새 판정을 복구하는 절차도 필요하다.
- **확정 중 권한 상실:** 현재 epoch만 따르라는 규칙과 이미 승인된 확정을 끝내라는 규칙의 관계를 정한다. 새 마스터는 진행 중 확정을 재배정하지 않고 격리하며, 이전 실행기는 새 일을 받지 않아야 한다. CVAT 변경 도중 무조건 멈추고 임의 복원하는 것은 안전한 인계가 아니다.
- **요청 최종 상태:** TASK 끝 보고의 8단계 이후 요청 완료를 누가 언제 쓰는지, 소유 실행기가 죽으면 어떤 복구 실행기가 그 요청을 넘겨받는지 명시한다. 확인을 고른 사람이 요청 정본까지 직접 바꾸면 단일 작성자 약속을 다시 우회한다.
- **실패 결과:** 기존 `replace_annotations`의 최초 remove가 try 밖이고 복원 결과는 로그 중심이다. 삭제/업로드/복원 성공 여부를 구조화해 `실패(복원됨)`과 `부분 반영`을 구별한다. 이전 b1 4절에 있는 전체 프레임 검사·사람 라벨 보호·프레임 매핑·직전 백업·반환/기록 호환 조건은 여전히 필요하다.

## 6. 실행한 확인과 시험 한계

`/tmp/egg_b2_probes.py`에서 외부 접속 없이 다음만 실행했다.

| 확인 | 결과 |
|---|---|
| 실제 drive_revisions.pin 함수를 AST로 분리해 가짜 svc 전달 | pin_count=1, revisions.update에 keepForever=True 전달 |
| 실제 12번 셀의 RUN_MODE 대입만 실행 | 기존 analysis 값이 cli로 바뀜 |
| 두 ARBITER 작성자가 같은 사본을 읽고 판정→heartbeat 순으로 저장하는 최소 모형 | round 11·처리 신호가 round 10·빈 신호 장부로 되돌아감 |

첫 둘은 실제 기존 함수/대입을 실행한 확인이다. 셋째는 **새 구현 시험이 아니라 설계가 허용하는 저장 순서를 보인 모형**이다. 셀 원문은 읽기용으로 `/tmp/egg_b2_cell*.txt`에 추출했다. 분석 wrapper·worker_cpu·Keeper·새 arbiter는 아직 없으므로 차단 성공, 정확히 한 번 처리, 새 회귀 시험 통과를 주장하지 않는다. 기존 전체 시험은 이번에 재실행하지 않았다.

구현 때 필요한 행동 시험은 다음과 같다.

- 분석에서 모든 셀의 실제 출력/하위 script·Drive pin이 허용 범위 밖에 쓰지 않는지, 12번과 30번 종료 후에도 분석 정책이 유지되는지.
- 승인 직전 취소/만료/모름, 부분 decision 게시, epoch 교체와 이전 실행기의 끝 보고, 관리 프로세스 실종을 함께 넣어 두 실행이 쓰지 않는지.
- CVAT 반영 전후 단계별 종료에서 복구 자료가 남는지, 사람이 고른 복구가 앞 실행과 겹치지 않는지.
- 신호 효과 후 장부 저장 전 종료, heartbeat 저장과 판정 저장 교차, waiting만 남은 재기상, STOP/RELEASE를 재시작 후 한 번만 적용하는지.
- 제출 후 분석 파일 변경/삭제·다른 TASK 매핑, 정리 중 모델 받기, snapshot 요약·15번 학습 입력·고정 시험 제외의 연결.

## 점검했지만 문제가 없던 항목

- 확정 신청을 심판이 승인한 뒤 첫 CVAT 쓰기를 허용하는 방향은 E1을 직접 다룬다.
- 시간 경과만으로 자동 복구하지 않고 격리하는 방향은 안전하다. 사람 선택 후 재허가 조건은 G1로 구분했다.
- CPU 장시간 작업의 프로세스 분리와 제어 전송 timeout은 기존 전역 모듈·rclone 잠금 문제를 줄인다.
- 관리 일 하나로 모델·데이터셋 변경끼리의 취득 교착과 학습/정리 동시 실행을 줄일 수 있다. 독자와 인계 문제는 별도다.
- TASK별 불변 manifest와 취합 요약 분리, trash를 runs 밖에 두기, requests.json을 수집기에 남기는 결정은 E12~E14를 반영했다.
- 생성·복원을 요청으로 옮겨도 새 TASK 복원의 이름 꼬리표 예외를 유지할 수 있다. 기존 TASK 임의 개명·TASK 삭제를 추가할 이유는 없다.
- ULD 자기 폴더의 신청/생존 신호를 읽는 규칙은 CVAT_UpLoader 읽기 전용 약속과 양립한다.
- 보안 비밀의 저장 위치·0600 임시 파일·웹앱 배포 금지 약속을 바꾸는 제안은 없다.

## 시간이 모자라 보지 못한 항목 및 검증 한계

- 3판 요청서의 여섯 질문과 E1~E14는 모두 다뤘다. 이전 전체 코드 체크리스트 재검토나 모든 셀의 실행 시험은 아니다.
- 실제 Drive 권한·지연·Apps Script 실행 시간·Kaggle 세션 한도는 요청서 범위 밖으로 남겼다. 외부 정책의 현행 수치를 조회하지 않았다.
- 실제 SDK wrapper를 통한 차단, CVAT 비동기 import 종료·복원 결과 비교, subprocess 강제 종료·GPU 학습 중단은 실행하지 않았다.
- 저장소 밖 LC앱·AA앱·ULD앱 코드는 보지 않았다. 화면에 필요한 프로토콜·자료 보존 조건만 검토했다.
- F7·F8은 판정하지 않았다. epoch·프로세스·관리 일의 권한 문제를 GPU 예약 문제로 확장하지 않았다.
- 새 구현이 없는 항목의 ‘확인함’은 설계 규칙과 실제 기존 호출 경로의 대조에 한정된다. 아직 없는 구현에서 오류를 실행 관찰했다는 뜻은 아니다.
