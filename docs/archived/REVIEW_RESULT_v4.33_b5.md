## 6. 확인 방법과 구현 때 필요한 시험

v4.32.0의 백업/export·취합·요청 소유·Drive scripts 로딩·학습 background push, 생성/복원 셀을 읽었다. 노트북 코드는 읽기 전용으로 `/tmp/b5_cell*.txt`에 추출했다. 외부 접속 없이 간단한 상태 모형 두 개를 실행해 (1) 신호의 정확한 옛 내용을 재적용하면 새 epoch 잠금이 돌아가는 것, (2) 이동 목록의 같은 원본 경로에 새 내용이 생길 수 있는 것을 확인했다. 이는 설계 반례를 설명하는 모형이며 실제 v4.33 동작 시험이 아니다.

구현 시험에는 다음을 추가할 필요가 있다.

- 서로 다른 TASK의 동시 백업/export 후 공용 재개 기록이 모두 남음(J1).
- 초기화 이동 중 인계·같은 경로 재사용·옛 이동 재개 시 새 버전을 건드리지 않음(J2).
- 완료 wake만 남거나 야간 미승인 pending만 남아도 반복 기동하지 않음(J3).
- 효과 게시 직후 종료→실행기 상태 진행→epoch 인계→신호 복구에서 새 상태를 되돌리지 않음(J4).
- B 확정 뒤 A의 늦은 commit이 나타나도 모델/데이터셋/시험 설정이 A로 돌아가지 않음(J5).
- B 승인 기간 안의 A 늦은 쓰기는 시간 감시만으로 탐지 불가임을 시험에 명시하고 별도 비교 적용(J6).
- 새 TASK 생성 성공·응답 유실 후 중복 생성 없이 확인 필요로 복구(J7).
- wake 예약 직후 및 push 접수 직후 종료, 보류 해제만 반영된 상태의 재시작(J8).
- 일반 신호의 M 위조·stopped·관리자 역할 위조 거절, scripts 변조 시 실행 거절(J9·J10).

## 점검했지만 문제가 없던 항목

- 동시성: ARBITER 단일 작성자, 상태 취합 전용 잠금, ULD 읽기 전용 경계, 전체 보고 식별과 부분 게시 검사.
- 스케줄링: waiting 예외를 명시적 결정으로 분리, 묶음 반납 뒤 다음 차례, 관리 환경 지정, 취합과 장시간 작업 분리.
- 복구: 선게시 복구 자료, 호출별 의도/결과, 권한 상실 시 복원 금지, 단계 정체 감시, 확인 필요를 완료로 표시하지 않음.
- 접근: 모드 수명/컨텍스트, 하위 API까지 factory 대상에 포함, 직접 저장·Drive pin 점검, Keeper 권한 재확인, deploy·키 저장 위치 명시.

## 시간이 모자라 보지 못한 항목 및 검증 한계

- 요청된 네 관점과 H1~H7은 모두 다뤘다. 기존 코드 전체의 별도 결함 재발굴이나 전 셀 AST 쓰기 목록의 완전성 증명은 아니다. 점검표 A·B의 전환은 실제 새 코드에서 다시 검사해야 한다.
- 실제 Drive 소유자·ACL·지연·이름 변경, Apps Script 시간/트리거 동작, Kaggle API/세션 한도, CVAT 버전별 비동기 요청 조회는 실측하지 않았다.
- 새 arbiter/access/worker_cpu/Keeper가 없어 새 행동 시험을 실행하지 않았다. 기존 회귀 시험은 설계 프로토콜의 안전성을 입증하지 못하므로 재실행하지 않았다.
- 저장소 밖 앱·ULD 구현·GitHub workflow 및 F7·F8은 범위 밖이다. 코드 로딩의 실제 편집 권한은 J10의 조건부 위험으로 남겼다.
- CVAT 펜싱 부재, 정상적인 몇 초의 Drive 비교-쓰기 틈, 트리거와 마스터가 모두 사라지면 앱을 여는 사람만 아는 한계는 새 발견으로 반복 집계하지 않았다.
