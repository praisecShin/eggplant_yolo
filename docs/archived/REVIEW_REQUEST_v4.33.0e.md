## 무엇을 어떻게 고쳤나

| 지적 | 고친 방법 | 시험 |
| --- | --- | --- |
| Q1 긴 처리 중 생존 신호가 끊김 | 생존 신호를 일하는 줄과 다른 스레드(`arb_io.Beat`)로 보냄. `worker_cpu.run`이 시작할 때 켜고 끝날 때 멈춘 뒤 '끝남'을 남김 | 처리기가 4분 걸려도 마스터가 실행기를 죽은 것으로 보지 않고 일이 끝까지 감 |
| Q2 실행형 일이 권한을 잃으면 잠금이 영영 '실행 중' | 새 보고 `stop_run`. 실행기는 게시하지 않고 멈춤을 보고하고, 심판은 실행 잠금을 '확인 필요'(`stop_reported`)로 바꿈. 취합 줄은 그냥 풂. 멈춤 보고가 있으면 `run_choice`를 15분 기다리지 않고 받음 | 권한 잃음 → '확인 필요' → '다시 하기' → 새 실행 번호 |
| Q3 사람 목록 옛 값을 무기한 씀 | 마지막 성공 뒤 20분이 지나면 입력에 `config` '모름'을 넣음. 그 회차는 새 접수·신호 처리·배정을 하지 않고, 보고 반영·만료·확정 승인만 함. 실패 중에는 1분마다 다시 읽음 | 20분 넘게 못 읽음 → 새 요청 접수 안 함, 배정된 일은 마침, 다시 읽히면 재개 |
| Q4 Keeper가 보류를 심판 요약에서만 읽음 | `arb/holds/*`를 직접 읽고, 아직 처리되지 않은 `stop__` 신호도 보류로 봄. 기한(`until`)은 Keeper가 따짐. 보류 파일이나 `ARBITER.json`을 못 읽으면 '모름' — 깨우지 않고 알림, 깨우기 신호는 거절하지 않고 미룸 | 요약에 없는 보류, 기한 지난 보류, 해제된 보류, 깨진 보류 파일, 처리 전 정지 신호 |
| Q5 다시 시도할 때 권한·보류를 다시 보지 않음 | 처음과 다시 시도가 같은 확인(사람 목록·상태·권한·수정 여부·보류)을 거침. 나이(10분)와 '이미 살아 있음'만 처음에만 봄 | 첫 시도 뒤 사용 중지·권한 없어짐·정지 걸림·신호 고쳐짐 → 다시 시도 안 함 |
| Q6 '해제하고 깨우기'가 해제 신호 전에 끊기면 이어 하지 않음 | 깨우기 기록에 `release_stop`을 남김. 이어 할 때 해제 신호가 없으면 먼저 채우고(있으면 건드리지 않음), 그 다음에 '끝남'을 적음 | 판정 3가지 + 가짜 Drive에서 끊긴 뒤 다음 실행, 두 번 실행해도 한 번만 씀 |
| Q7 형태가 틀린 JSON이 판정 루프를 죽임 | `snapshot`이 객체가 아닌 JSON을 그 파일만 '모름'으로 넘김. rclone 목록의 형태도 확인. 심판은 형태가 틀린 실행기·요청·신청·신호 파일을 버리고 알림을 남김. 만든 시각은 숫자와 ISO 문자열을 모두 받음(`to_ts`). 그래도 판정이 예외를 내면 그 회차만 건너뜀. Keeper도 객체만 받음 | 배열·문자열 JSON, 숫자가 아닌 `hb`, 섞인 `created`, 판정 예외 |
| Q8 밤에 아무 신호로나 깨움 | 밤에 깨우는 신호 종류를 `confirm_choice`·`cancel`·`release`·`run_choice`·`adopt_choice`로 한정 | 종류별 |
| Q9 '할 수 있는 일 수'·새 실행기로 깨우지 않음 | 심판 요약에 `executor_wait`·`workers`를 추가. Keeper는 `runnable > 0`이면 깨우고, 실행기를 기다리는 일이 있을 때 심판이 모르던 실행기가 나타나면 깨움. 요약은 같은 시간대(낮·밤)에 계산한 것만 씀 | 밤 5가지 |
| 참고: 회차가 멈춘 심판에 다시 자격 | 자격 후보와 '켜지는 중' 판단에서 빼고 알림. 새 마스터를 깨움 | 1가지 |
| 참고: 자동 깨우기 재시도 | 10분 간격, 3번 연속 실패하면 메일 한 번과 30분 간격, 살아나면 되돌림 | 5가지 |
| 참고: rclone이 만든 시각을 주지 않음 | 거절하지 않음. 수정 시각으로 순서만 정하고 회차 요약에 `no_btime`을 남김 | 1가지 |

## 검토 질문

### A. b11 수정

1. Q1~Q9가 해결됐는지 판정해 주세요. 지난번 재현 스크립트(`/tmp/egg_b11_probes.py`, `/tmp/egg_b11_keeper_probes.js`)가 남아 있으면 다시 돌려 주세요.
2. **Q1:** 생존 신호 스레드와 일하는 줄이 같은 저장소 객체·같은 실행기 객체를 함께 씁니다. 두 줄이 동시에 쓰는 상태(`Executor`의 필드, `RcloneStore`·`Cache`)에 경합이 있는지 봐 주세요. 또 일하는 줄이 정말 멈췄는데(무한 대기) 생존 신호만 계속 나가는 경우를 심판이 어떻게 보게 되는지, 지금 설계(확정 단계의 CVAT 호출 시간 한도는 2단계)로 충분한지 의견을 주세요.
3. **Q2:** `stop_run` 뒤 '확인 필요'에서 '끝난 것으로'를 고르면 `complete_run`을 거칩니다. 권한을 잃은 실행기가 버전 경로에 일부만 쓴 산출물이 채택될 수 있는 경로가 있는지 봐 주세요.
4. **Q3:** `config` '모름'일 때 멈추는 범위(새 접수·신호·배정)와 계속하는 범위(보고·만료·확정 승인·인계)가 맞는지 봐 주세요. 특히 그동안 취소·정지 신호가 처리되지 않는 것이 받아들일 만한지 의견을 주세요.
5. **Q4~Q6:** 새 반례를 찾아 주세요.
   - 보류가 있는데 깨우는 경우
   - 보류가 없는데 영영 깨우지 않는 경우 (예: 거절로 끝난 정지 신호, 완료 기록을 못 읽은 경우)
   - 해제 신호가 두 번 나가거나, 깨우기는 실패했는데 해제만 반영되는 경우
6. **Q9:** '같은 시간대에 계산한 요약만 씀' 규칙으로 놓치는 경우(예: 낮 18:59에 계산, 밤 19:01에 야간 승인된 일)가 `next_wake_at`으로 모두 덮이는지 봐 주세요.
