| 대상 | 판정 |
|---|---|
| 확정 신청 식별 | 파일 이름과 신청 필드는 해결. 승인·끝 보고 전체 튜플의 일치 조건은 부분 반영(H7). |
| 모름 전파 | 자격·요청·workers 목록 실패의 전체 승인/회수 보류는 해결. 보고 반영도 실패한 입력에 의존하는 잠금 해제를 해서는 안 된다는 구현 시험이 필요하다. |
| 부분 게시 | assign 먼저, 같은 decision·epoch·S·gen, 일치 TASK만 시작은 반영. 전체 튜플 검사를 점검표에 구체화할 필요가 있다(H7). |
| 재시작 다시 발급 | 같은 소유자·decision을 새 epoch로 발급하고 늦은 구 epoch 덮어쓰기를 복구하는 절차는 반영. 살아 있음만으로 관리 실행의 실제 게시 완료를 판단하지 않는 조건은 H3. |
| 확정 중 권한 상실 | 다음 호출·복원 금지 및 재발급 대기는 반영. 이미 확인한 호출의 잔여 위험은 H1. |
| 요청 최종 상태 | 마지막 묶음 후 소유 실행기가 이름 변경, 사망 시 재배정은 명시됨. 확인 필요 TASK를 남긴 요청은 최종 완료할 수 없고, 복구 요청 결과가 원요청 TASK 결과에 연결되어야 한다는 시험도 필요. |
| 구조화된 실패 | 점검표 F에 최초 remove·복원 결과·전체 프레임·기존 반환/기록 호환이 이관됨. |

G5~G8 및 b2 3절의 factory·하위 API·자체 세션·CLI·직접 파일 쓰기·Drive pin·입출력 분리·제출본·읽기 해시 항목은 A~D에 대응한다. b2 5절의 백업 자동 결합·waiting·GPU 기동·정지·생성/복원·23번 OAuth·27번·스냅숏 소비자·청소·프로세스 root 분리는 G에 대응한다. 해결 방향 자체는 재검토하지 않았다. 누락으로 구체적으로 남는 것은 H7의 보고 식별/상태 요청 완료 연결이다. F에는 작업번호를 필드에도 넣고, H의 부분 게시 시험에는 전체 식별 튜플을 명시하는 편이 좋다.

## 4. 감시·재시작 및 기능 손실 대조

감시 표는 요청된 여섯 핵심 기능을 모두 포함한다. 판정 루프 회차와 마스터 heartbeat를 구별하므로 heartbeat만 도는 마스터도 Keeper가 찾을 수 있다. 마스터와 Keeper가 함께 멈추면 자동 복구는 못 하지만 앱과 마지막 시각으로 사람이 알아챌 경로는 명시됐다. 다만 Google 트리거 실패 메일은 트리거가 삭제되거나 실행 자체가 없는 경우의 보증으로 볼 수 없다. 이때 보장은 앱을 실제로 여는 사람까지다.

재시작 대조도 요청·승인·잠금·신호·관리/취합·waiting·미처리 정지를 포함한다. 감시 표의 CPU 작업 생존 신호는 프로세스가 살아도 작업이 진행하지 않는 교착을 직접 증명하지는 않는다. 단계 기록이 일정 시간 변하지 않는 경우도 정기 점검의 이상 목록에 포함하고, Colab 전용 관리 일이 실행기 부재로 대기 중인 상태를 장애와 구별해 보여 주면 조용한 대기를 줄일 수 있다. 구체적인 작업별 한도는 이번 실측 범위 밖이다.

현재 `Code.gs`의 `triggerGhDispatch_`(719~731행)는 repository_dispatch HTTP 요청과 204 확인만 한다. `wakeUpCpuMaster_`(639~659행)가 전달하던 CPU slug·GPU 끔·기동 이유·시각을 직접 push metadata/기록으로 옮기면, **이 파일에서 확인되는 기동 기능**의 필연적인 손실은 없다. 주간 유지·야간 승인·STOP 보류·수동 기상 의미는 새 주체로 이관해야 한다. 특히 기존 `wakeCpuMasterNow` 777~791행은 STOP을 지우고 기동하므로 새 관리자 전용 동작에 대응시켜야 한다. 외부 GitHub workflow 소스는 비교 폴더에서 찾지 못했으므로 그 안의 소스 준비·환경 설정·재시도까지 없어져도 되는지는 단정하지 않는다.

## 점검했지만 문제가 없던 항목

- 복구 자료는 CVAT 첫 쓰기 전에 실제 바이트를 게시·검증하도록 바뀌었다. 게시 중 실패하면 쓰지 않으므로 불완전 자료만으로 CVAT 변경을 시작할 이유가 없다.
- `submissions/`의 고정 복사·해시 검증·새 제출 ID·분석 폴더와 별도 보존은 G7의 분석 파일 재계산/삭제 문제를 다룬다. 무기한 보존은 명시적 결정이므로 그 자체를 결함으로 세지 않았다.
- 받는 중 예외는 읽기 백업/export에 한정했다. 기록한 updated_date는 요청 시 관측한 버전이며 export zip 내용과 원자적으로 같은 버전임을 보장한다고 해석해서는 안 된다.
- 23번 Colab 전용 지정은 기존 Drive OAuth 기능을 보존한다. 준비된 Colab 실행기가 없을 때 즉시 실행되지 않는 것은 잘못된 Kaggle 배정보다 안전하다.
- people 번호 재사용 금지·stopped 유지·등록 안 된 세션의 읽기 제한은 명시됐다. 10분 갱신에 따른 권한 회수 지연은 문서에 드러난 한계다.
- ARBITER 단일 작성자, 취합 최신 tracked 받기, 새 epoch 재발급, 부모 계획 종료 전 GPU 멈춤 게시가 명시됐다.

## 시간이 모자라 보지 못한 항목 및 검증 한계

- 요청한 일곱 질문은 모두 검토했다. 3판에서 해결로 판정된 E1·E6·E8·E12~E14와 변경 없는 절을 다시 전면 검토하지 않았다.
- 실제 Drive 권한·지연·파일 소유자/생성 시각의 서비스별 동작, Apps Script 시간, Kaggle 한도, CVAT 버전별 import 조회는 실측하지 않았다. 인증 관련 판정은 외부 API의 현행 동작을 단정한 것이 아니라 설계에 필요한 검증 조건의 누락이다.
- 새 arbiter/access/Keeper/worker_cpu 구현이 없어 행동 시험을 실행하지 않았다. 기존 코드 회귀 시험도 설계 변경을 검증하지 못하므로 이번에는 재실행하지 않았다.
- 저장소 밖 앱·GitHub workflow, F7·F8은 검토하지 않았다. 키 보유와 실행 소스의 실제 ACL 확인은 H6의 조건부 위험으로 남겼다.
