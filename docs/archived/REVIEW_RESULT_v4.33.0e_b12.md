| 조건 | 첫 heartbeat 쓰기를 막고 실제 worker_cpu.run을 종료시켰다. 반환 직후 파일은 stopping=true였으나 막은 쓰기를 풀자 false로 되돌아갔다. 기본 3분 동안 종료 세션을 다시 살아 있다고 볼 수 있다(기존 hb의 나이에 따라 기간은 달라짐). |
| 확신 | 확인함 — 실제 run/finally·Beat·LocalStore, 지연 쓰기 주입 |
| 제안 | 진행 중 생존 신호 쓰기가 끝나기 전에 최종 종료 쓰기를 시작하지 않도록 순서를 보장한다. 정상 경로뿐 아니라 저장소 지연·종료 경합 시험을 둔다. |

## 4. 요청한 추가 의견

### 생존 신호 스레드·무한 대기

heartbeat는 Executor의 seq·sent·mem·touched를 수정하지 않고 me/fp/caps/clock을 읽어 worker 파일에만 쓴다. 작업 줄의 snapshot은 Cache를 주지 않으며 Beat도 Cache를 사용하지 않는다. 따라서 현재 두 줄 사이에 Cache 경합을 새로 확인하지는 않았다. RcloneStore의 remote/runner/timeout은 통상 읽기만 하며 서로 다른 파일의 rclone 호출 자체가 같은 Executor 메모리를 바꾸지는 않는다. 같은 worker 파일을 동시에 쓰는 종료 경계는 R7이다. LocalStore는 동일 파일 쓰기에 같은 `.tmp` 이름을 쓰므로 그 경계에서 추가 충돌도 가능하다.

처리기가 무한 대기하면 Beat가 계속 살아 있으므로 심판의 사망 만료는 작동하지 않는다. 관리 잠금은 running, 승인된 TASK는 승인 상태에 남을 수 있다. 자동 재배정하면 옛 쓰기와 겹칠 수 있어 생존 신호를 끊는 것으로 해결해서는 안 된다. 1b 뼈대 단계에서 timeout 구현을 2단계로 남기는 것은 가능하지만, 운영 연결 전에는 CVAT 호출 한도뿐 아니라 prepare/fetch/run·외부 프로세스의 진행 시각·시간 한도·격리/사람 확인 경로도 정해야 한다. 설계에 이미 표시한 ‘멈춘 것 같음’ 미구현은 별도 새 발견으로 세지 않았다.

### stop_run 이후 부분 산출물

`run_choice=done`은 해당 버전의 `_files.json`이 없거나 files가 비었거나 verified가 없으면 거절한다. 따라서 일부 파일만 쓰고 manifest를 완성하지 않은 보통의 권한 상실 경로가 곧바로 채택되지는 않는다. complete_run의 CURRENT 모름 검사와 채택 판정도 유지된다.

다만 심판은 verified라는 표시를 신뢰하며 실제 파일 바이트·해시·실행 ID·decision·gen을 여기서 검증하지 않는다. 현재 시험도 임의 `files={a:h}, verified=true`만 놓고 채택시킨다. ‘부분 파일이 절대 채택되지 않는다’는 운영 보장은 아직 증명되지 않았다. 2단계 Handlers는 버전 파일을 모두 게시·재검증한 뒤 마지막에 manifest를 확정하고, 이후 불변으로 유지해야 한다. 파일 누락·해시 불일치·다른 run/decision/gen·manifest 이후 변조·권한 상실 중단을 실제 연결 시험에 넣어야 한다. 이 역할이 아직 연결되지 않은 점을 1b의 새로운 확정 결함으로 중복 보고하지 않았다.

### config 모름 동안 정지·취소

현재 구현은 11/14 합의대로 동작한다. 이미 배정된 일에 대한 취소·정지는 설정 복구까지 처리되지 않으며, held TASK의 확정 신청도 계속 승인될 수 있다. ‘새 배정을 안 함’과 ‘CVAT에 새 쓰기를 시작하지 않음’은 다르다. 오래된 권한으로 새 제어 신호를 승인하지 않는 선택은 일관되지만 즉시 정지 수단으로는 충분하지 않다. CTRL 화면에 config 모름·신호 미처리를 표시하고 긴급 시 실행 세션 및 CVAT 서버 작업을 확인하는 별도 절차를 둬야 한다. 설계의 ‘즉시 막으려면 관리자 정지’ 문구는 이 장애 조건을 반영해야 한다.

### Keeper 나머지 경계

- 이미 거절/완료한 stop의 signal_done 파일이 목록에 있으면 내용이 rejected여도 처리된 것으로 보므로 보류로 되살리지 않는다. 반면 signal_done의 존재 자체가 누락되면 미처리 stop으로 보아 막는다. 안전하게 멈추는 선택이라도 장기 장애를 알릴 복구 경로는 필요하다.
- 동일 origin_signal의 해제는 create-only라 정상 재실행에서 중복 생성하지 않는다. 해제 신호만 존재한다는 이유로 자동 기동하지 않는 계약도 유지된다.
- 해제 신호를 먼저 쓰고 push하므로 노트북 해시 불일치·키 없음·API 실패에도 해제가 남는다. 가짜 Drive에서 `failed/notebook_hash_mismatch`와 해제 파일 1개를 확인했다. 설계의 ‘해제를 만들고 깨움’ 순서에는 맞지만 원자적 성공은 아니다. CTRL은 ‘해제 게시됨 / 기동 실패’를 따로 보여야 한다. 특히 아직 살아 있는 실행기는 해제의 영향을 받을 수 있으므로 이를 전부 실패·아무 효과 없음으로 안내해서는 안 된다.

## 5. 배포 계획 보완과 2단계 전 최소 목록

옛 Apps Script 트리거를 새 Keeper보다 먼저 끄는 방향은 맞다. 다만 트리거 삭제 전 이미 시작한 실행이 끝났는지 확인해야 하고, 옛 앱 주소를 7일 보존하더라도 쓰기·요청 제출은 막아야 한다. R4의 drain·요청별 전환 대장을 먼저 확정한다. 롤백은 새 산출물의 호환성/보존 방침과 최신 요청 결과를 반영해야 하며 폴더 일부 복원만으로 끝내지 않는다. 실제 중복 쓰기·백업 누락·소유자 판정 오류는 2시간 대기 없이 즉시 쓰기를 중지할 조건으로 둔다.

‘전환 전 실제 시험’에는 다음을 보탤 필요가 있다(이번 검토에서 실제 계정 시험은 수행하지 않음).

- 실제 계정 조합에서 관리자 폴더 읽기 허용과 K/G의 수정 거절, 공유 폴더의 G 소유 grant 유지, 덮어쓴 뒤 소유자 유지. 단순 읽기 성공만으로 접근 분리가 검증되지는 않는다.
- 보류/해제·기동 요청 전후 중단, 응답 유실 후 기동 여부 불명, wake_done 읽기 회복, 실제 트리거 실행 시간대 및 18:59→19:01 전환.
- 작업자 종료와 CVAT 서버 import 종료의 차이, 승인 뒤 네트워크 timeout, 권한 회수 후 복원 금지, 업로드 전 백업·사람 라벨 보호를 실제 시험 TASK에서 확인.
- 옛 taken/running/백업 대기를 섞은 전환 예행 연습과, 새 요청이 일부 완료된 뒤 되돌리는 왕복 예행 연습. 메일·생존 시각만이 아니라 요청별 실제 효과를 대조.
- 승인된 배포 파일 검증 후 바이트 사용, 변조/하한 버전 실행 거절, 비밀 값이 요청·상태·예외·메일에 남지 않는 연결 시험.

2단계 시작 전에 고칠 최소 목록은 다음과 같다.

1. R1~R3의 입력 격리·정지 복구·기록 모름 처리를 수정하고 정상 요청 진행 및 장애 회복 시험을 추가한다.
2. R6·R7의 시간대 전환과 종료 쓰기 순서를 보완한다.
3. R4·R5의 전환·롤백·ULD drain 계약을 문서에서 확정한다.
4. 2단계 구현 항목으로 진행 감시/호출 시간 한도, manifest 최종 검증, config 모름의 긴급 정지 절차를 명시한다. 실제 계정 검증은 연결·운영 승인 조건으로 남긴다.

## 6. 점검했지만 문제가 없던 항목

- 지정된 4개 시험 전체, 기존 중단 경계 수렴·epoch/gen 재보고·완료 의존성 모름 처리 회귀.
- stop_run 식별과 needs_check 전이, redo의 새 실행 ID, 취합 잠금 반납.
- 설정 20분 유효기간·재조회와 합의된 새 접수/신호/배정 중단 범위.
- 현재 보류 파일·기한 판정, 깨진 보류/회차 JSON의 보수적 처리, 재시도 권한 재확인.
- Keeper의 야간 신호 제한, 동일 시간대 실행기 대기 깨우기, 자동 실패 간격과 멈춘 심판 후보 제외.
- 검토한 새 Keeper 경로에 doGet/doPost 없음, Kaggle 응답 본문·키를 상태/메일에 남기지 않음. 실제 비밀 값은 사용하지 않음.

## 7. 시간이 모자라 보지 못한 항목·검증 한계

- 기존 v4.32 전체 회귀 시험 및 노트북 셀 일치·기존 업로드 경로의 전수 재검토는 하지 않았다. 이번 변경은 아직 연결 전인 1b에 집중했다.
- 실제 Apps Script·Drive·rclone 원격·Kaggle·CVAT 동작, 외부 API의 현재 형식과 서비스 한도는 검증하지 않았다. 지정 금지에 따라 실제 서비스에 접속하지 않았다.
- 새 실행형 stop_run과 모든 중간 쓰기/읽기 실패 조합의 전수 탐색, 모든 입력 필드의 퍼징은 하지 않았다.
- 2단계 Handlers·노트북·앱 연결은 아직 없으므로 실제 백업/업로드 보호·manifest 검증·진행 감시·구버전 차단의 종단 보장은 검증할 수 없다.
