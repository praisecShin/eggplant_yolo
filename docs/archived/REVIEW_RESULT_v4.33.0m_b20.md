## 검토 질문별 보충 판단

### 1·2. 신원 재검사와 영구 대기

- **원 신호가 정말 없음:** G 해제에서는 origin_missing으로 끝낸다. 원 소유자의 권한을 입증할 원본이 확정적으로 없는 경우의 거절은 안전한 선택이다. 이를 ‘실제 권한 철회’와 같은 문구로 표시할지는 별개지만, 임의 해제는 하지 않는다. 해당 거절을 복구하려면 새 신호가 필요하다.
- **원 신호를 못 읽음:** 실제 파일 부재와 구분하지 못하는 Q2다. 원 신호의 경로를 unknown으로 아는 경우에는 보류해야 한다. 원 신호가 아닌 G release 자체를 읽지 못하면 signals 순회에서 빠져 그 회차에는 진행하지 않는다.
- **사람 목록 일부를 못 읽음:** MasterLoop는 사람 목록의 필수 칸·형태·중복을 전체 검사한다. 읽기 실패나 일부 항목의 형태 오류를 정상 목록으로 채택하지 않고 기존 설정을 사용하며, 20분을 넘기면 config 모름으로 신호 처리 자체를 멈춘다. 이 캐시 유예는 기존 설계다. 문법·형태가 정상인 ‘사람이 일부 빠진 목록’은 실제 삭제와 구별할 수 없어서 not_registered로 분류한다. 파일 목록/읽기 실패를 정상적인 빈 people로 바꾸는 것은 허용해서는 안 된다.
- **G가 신호 소유자:** origin_signal이 있는 release만 허용한다. 다른 종류는 g_not_allowed로 거절한다. 원 소유자가 다시 G이면 system 신원이므로 origin_not_person으로 거절한다. G 파일 자체가 일반 관리자 권한을 얻는 것은 아니다. 정상 사람의 현재 release 권한 철회는 공식 회귀에서 적용되지 않는다.
- **계획의 영구 보류:** owner가 계속 모름이면 관리자가 복구할 때까지 계획은 유지된다. 자체 만료·재시도 상한은 없다. 원 처리 신호 자체가 사라지거나 매번 읽기 실패하면 그 신호는 process_signals에 들어오지 않아 계획만 남을 수 있다. 미완료 계획을 자동으로 지우지 않는 설계와 맞지만 복구/모름 표시가 필요하다. 이번 수정의 ‘모르면 보류’를 완료로 바꿔 대기열 크기를 줄여서는 안 된다. Q2는 이 정상 보류와 달리 잘못 영구 종료시키는 문제다.

### 3. 중복 판정 파일·밤 종료·Keeper

- 한 목록 안의 같은 경로를 감지하는 구현은 맞다. 서로 겹치는 두 목록이 동일한 정상 파일을 각각 돌려주는 것은 물리 중복의 증거가 아니므로 이 사실만으로 중복으로 보지 않는 선택도 타당하다. 공식 회귀가 두 경우를 나눠 확인한다.
- arb/의 중복을 보호 모드와 구별해 file/dup 모름으로 전달하는 것 자체는 이번 결정과 맞다. **모름이 이후 판단에서 안전하게 소비되어야 한다는 조건이 빠진 Q1은 해결되지 않았다.**
- 실제 MasterLoop에서 밤에 정상 stop을 처리하고 hold 목록에 중복을 주었다. unknown에는 file/dup이 남고 last_clean_at이 last_run_at보다 오래되어 `exit_reason=None`이다. 따라서 이 회차를 근거로 night_idle 종료하지는 않는다(`b20_night_probe.log`). 다만 wake 요약의 holds는 빈 목록이며, 낮의 새 배정을 막지도 못한다(Q1). 최대 11.2시간 종료는 별도 정책이다.
- Keeper는 최신의 같은 세션/epoch 회차가 있으면 살아 있는 심판으로 보아 새 마스터를 깨우지 않는다. 심판이 오래되었을 때 Keeper의 hold 읽기가 실패하면 holds=null이 되어 자동 깨우기를 미룬다. 같은 이름의 active 보류 두 개가 읽히는 경우에는 ID 집합으로 하나의 정지로 계산하여 자동 깨우기를 막는다(`b20_keeper_probe.log`). Keeper 자체는 물리 중복 판정기를 공유하지 않으므로 ‘중복 파일 정리까지 모든 제어가 차단된다’고 일반화할 수는 없다.
- T18은 실제 rclone의 중복 목록·cat·moveto·rcat과 CTRL 모름 표시를 검증하는 적절한 후속 시험이다. 다만 이미 로컬 판정 코드에서 재현한 Q1을 T18까지 미룰 이유는 없다.

### 4. 시각 검사·최신 장부·fail_since

- **Z2의 검사 범위:** event.at·batch.at은 필수의 해석 가능한 문자열, attempt_at은 존재하면 해석 가능한 문자열이다. batch.at 누락과 attempt_at='broken'은 실제로 거절된다. 매 수집 회차의 readPending_에서 검사하므로 사건이 추가되지 않아도 손상 목록이 조용히 유지되지 않는다.
- updated는 날짜로 검사하지 않고 문자열만 확인한다. Date.parse 가능한 시각도 ISO 정규형을 강제하는 것은 아니다. 따라서 ‘같은 형식’은 시간대와 소수초 자릿수까지 같다는 뜻이어야 한다(Q3). 실제 동일 형식의 Z3 공식 회귀는 통과한다.
- 시각의 과거/미래 범위와 now와의 관계는 검사하지 않는다. 예를 들어 현재보다 한 시간 뒤의 유효한 attempt_at은 형식 검사를 통과하고 그 시각+10분까지 대기한다(`future_attempt` 재현). 시간 형식 오류는 해결됐지만 시계가 앞으로 갔다 돌아온 경우의 지연 상한까지 보장하지는 않는다. 이는 새 높음 발견으로 올리지 않았으며, 운영 시각 전제와 미래 시각 처리 방침은 2b 또는 예행 연습에서 정할 수 있다.
- 장부의 `>=`는 ‘더 최신일 때만’이라는 설명보다 넓다. 동일 TASK·kind·updated가 사건 키이므로 정상 중복 재시도에서 동률 덮어쓰기는 같은 사건의 연결 갱신이 될 수 있다. 별도 동률 순번 정책 없이 모든 다른 사건을 구별한다고 해석해서는 안 된다. 확인된 퇴행은 Q3·Q4다.
- fail_since는 전체 수집이 실패한 첫 run.time으로 정해지고, 이후 실패에는 고정된다. 성공하면 null, 다음 실패에는 새 시각이다. Keeper는 last_ok가 있으면 그것을 우선하며, 성공 이력이 없으면 fail_since를 쓴다. `/tmp`의 실제 0m 산출물을 읽은 결과도 Date.parse(fail_since)와 같았다.
- 자동 요청 flush의 오류처럼 collect가 의도적으로 `ok=true`와 auto.error를 남기는 경우는 fail_since의 ‘전체 수집 실패’에 포함되지 않는다. fail_since가 모든 개별 하위 기능의 성공을 감시한다고 해석하면 안 된다.

### 5. 중요 알림을 현재 상태로 줄일 때의 순서

- 현재 0m 생성 항목은 mail/push 각각 `(t, group)`별 마지막 항목을 고른다. 기존 대기열 뒤에 이번 전이를 붙이므로, 같은 채널에서 오래된 ‘들어감’을 최신 ‘끝남’ 뒤에 재전송하는 경로는 이 로직에서 발견하지 못했다.
- 추가 재현은 들어감→끝남→들어감→끝남 사이에 전송을 계속 실패시켰다. 대기열에는 mail·push 각 한 개의 끝남만 남고 n=4가 됐다. 전송을 복구하면 끝남만 전달되고 대기열이 비었다. 단일 호출에서 여럿 합치기뿐 아니라 호출 사이의 누적도 확인했다.
- 메일과 푸시는 별도 채널이므로 수신 시각·성공 여부가 서로 같다는 보장은 없다. 한 채널에서 이미 전달된 진입과 다른 채널에서 먼저 전달된 종료가 사람에게 다른 순서로 도착하는 것까지 서버의 전송 목록 정리로 막지는 못한다. 이번 검사에서 애플리케이션이 채널 내부의 현재 상태를 역순으로 선택한 반례는 없었다.
- group이 없는 옛 대기열 항목은 이번 압축 대상이 아니다. 이미 남은 0l 대기열을 승계할 계획이면 예행 연습에서 이전 형식 정리 여부를 확인해야 한다. 아직 2b 전이므로 이 전환 점검을 착수 차단 사유로 보지는 않는다. 외부 발송 직후 기록 전 중단의 중복 가능성도 기존 한계다.

## 2b 전에 꼭 고칠 최소 목록

1. **Q1:** file/dup 모름의 판정별 의존성 차단. 특히 중복 hold 아래 새 배정·GPU 기동 금지, 중복 plan/done의 재생성·덮어쓰기 금지를 확인한다.
2. **Q2:** G 해제의 원 신호 읽기 모름과 확정 부재/권한 철회를 구분한다. 읽기 실패→완료 없음→복구 후 기존 계획 진행의 여러 회차 시험을 추가한다.
3. 위 두 수정 후 지정 시험과 두 퍼징을 다시 실행한다. 현재 퍼징은 경로 중복·파일 부재와 unknown 조합·권한 재검사의 회복까지 전수 생성하지 않으므로 추가 고정 회귀가 필요하다.

## 2b 안에서 또는 예행 연습에서 다룰 항목

- **2b 안에서:** Q3의 시각 정규화·비교, Q4의 skipped를 포함한 최신 장부 보존. 미래 attempt_at 처리와 같은 updated 동률 정책도 이때 명확히 할 수 있다. 고치지 않고 넘기면 알려진 한계와 운영 전제를 명시해야 한다.
- **예행 연습 T18:** 실제 Drive 동일 이름 파일의 감지·관리자 정리, rclone cat/moveto/rcat, 실행기 완료 쓰기, CTRL 모름 표시. Q1 수정 후 관리자가 하나를 남길 때까지 해당 처리가 실제로 보류되는지 확인한다.
- **예행 연습:** 실제 CVAT updated의 표기, 수집기 최초 연속 실패 알림, 메일·ntfy 실패→복구, 이전 outbox 형식 승계, 실제 계정별 Drive 소유자 관측.
- **2b 처리기 연결 시험:** 백업 선행·사람 라벨 보호·정지와 확정 경계·단일 요청 소유·게시 잠금은 실제 처리기와 가짜 CVAT를 연결해 검증한다. 이번 공통 계층 시험 통과가 이 항목을 대신하지 않는다.

## 점검했지만 문제가 없던 항목

- 지정 일반 시험 642개, 기본·seed=7 퍼징 각각 9개 항목 통과.
- Z1의 신호 owner 모름 보류·읽기 복구 후 완료, 실제 release 권한 철회 시 미적용 효과 차단.
- Z2의 잘못된 attempt_at·batch.at 누락 차단과 변화가 없는 회차의 목록 검사.
- Z3의 같은 정규형 export 최신 기록 보존과 history 추가.
- Z4의 목록 내부 중복 감지·겹치는 목록 구분·신규 중복 요청 접수 차단·duplicate_path 알림.
- 중복 판정 모름 회차를 밤의 clean 회차로 세지 않는 MasterLoop·exit_reason 동작.
- Z5의 최초 실패 시각 고정·성공 시 초기화·재실패 새 구간·실제 수집기 산출물과 Keeper 연결.
- 중요 알림의 채널별 최종 상태 보존·전송 실패 중 횟수 누적·복구 후 전송.
- 변경하지 않은 CTRL앱의 기존 제어 회귀 32개.

## 시간이 모자라 보지 못한 항목·한계

- 제공되지 않은 `rLog/b19_*` 원본 스크립트·로그의 직접 재실행은 못 했다. 현재 공식 회귀와 이번 재구성 재현 결과를 구분해 기록했다.
- 실제 Drive·CVAT·Kaggle·Apps Script 계정·메일·ntfy·claude.ai 커넥터에는 접속하지 않았다. 특히 물리 중복 파일에 대한 실제 rclone 읽기·완료 쓰기는 T18 대상이다.
- 모든 판정 종류의 중복·모든 부분 쓰기·다중 파일 모름·권한/시간 변화 조합은 전수 검사하지 않았다. Q1은 실제 snapshot을 사용한 대표 hold/plan/done 사례다.
- v4.32 전체 회귀·노트북 셀 전체 일치·Kaggle IPython 호환성과 아직 연결되지 않은 2b·LC·AA 종단 처리는 이번 범위 밖이다.
- 외부 알림 채널의 실제 배달 순서·0l outbox에서 0m으로의 실환경 전환은 확인하지 않았다.
