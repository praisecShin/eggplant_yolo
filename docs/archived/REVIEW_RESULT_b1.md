### E5 — 줄별 폴더만 나누어도 기존 전역 모듈·세션 기록은 함께 바뀜

| 칸 | 내용 |
|---|---|
| 번호 | E5 |
| 심각도 | 높음 |
| 관련 항목 | 네 줄 구성, 약속 9, 검토 질문 2 |
| 위치 | 설계 86~93행; CPU 마스터 378~398, 827~862, 887~951, 965~972행; `ctt.write_sharded` 2471~2494행 |
| 무엇이 문제인가 | 같은 프로세스의 줄은 `cvat_backup` 전역 설정, `rb.add_history`의 임시 치환, `_STATE`, 같은 SESSION_ID의 CSV shard를 공유한다. 현 작업 함수는 heartbeat도 직접 부른다. 따라서 ‘각 줄은 다른 파일만 쓴다’는 표만으로 현재 함수를 병렬 호출할 수 없다. |
| 일어나는 조건 | 작업 두 줄이 다른 TASK의 backup을 처리하면서 `cb.TASK_IDS`·MODE·조직을 바꾸거나, 취합 줄이 `rb.add_history`를 치환한 동안 작업 줄이 history를 쓴다. 두 줄이 같은 shard를 `write_sharded`하면 PID가 같은 임시 파일을 함께 쓴다. |

| 제안 | 작업 설정은 호출별 객체로, heartbeat 쓰기는 전담 줄로, TASK 기록은 함수 인자로 분리한다. shard는 줄별 파일로 나누거나 한 기록 쓰기 큐로 직렬화한다. `rb.add_history` 치환과 공용 폴더 전체 받기/올리기를 없애고, 같은 세션 안에서도 요청·자원별 실행을 하나로 제한한다. |

## 3. 네 줄과 심판 회차를 기존 코드에 옮길 때

현재 CPU 마스터는 **주 실행 루프와 heartbeat 스레드**다. 작업·취합이 주 루프에서 순차 실행되므로 네 줄 설계는 함수 이름을 나누는 것보다 큰 변경이다.

| 줄 | 그대로 가져오면 남는 쓰기/공유 상태 | 필요한 분리 |
|---|---|---|
| 심판 | 기존 `lease_tick`은 heartbeat에서 호출되고 `_STATE.owner`도 바꿈 | 임대 정본 쓰기는 심판 한 곳으로 이동; heartbeat는 후보·자기 진행 상황만 게시 |
| 작업 1~2 | `handle_lc`가 `send_heartbeat_once` 호출, `cb` 전역 설정, export/pending·shard와 광범위 push | 요청/자원별 실행 컨텍스트, heartbeat 전달 큐, 줄별 임시 폴더·게시 목록 |
| 취합 | `repair_pending`·`settle`은 상태 파일 외 CSV/요청도 씀. `rb.add_history` 치환 후 TASK 기록 쓰기, `snapshots`는 manifest 갱신 | 요청 완료는 소유 작업 줄로, TASK 이력은 TASK 잠금/신호 경로로. 상태 계산은 읽기 사본에서 하고 허가된 파일만 게시 |
| 취합 | 설계 92행은 ‘기록 합치기’를 맡기지만 238·286행은 청소 셀에 맡김 | ‘읽어서 합쳐 보기’인지 원본을 대체하는 compaction인지 구별. 기존 compact_shards 호출을 그대로 옮기지 않음 |
| 생존 신호 | 시작·작업·종료 경로에서도 같은 함수 호출, `_STATE.busy`를 여러 줄이 덮음 | heartbeat 파일 작성자는 하나, 각 줄 상태는 별도 칸/이벤트로 전달 |
| 모든 줄 | 하나의 `_RC_LOCK`, 같은 BASE, 모듈 전역·같은 세션 shard | E5·E6. 독자용 pull이 작업 중 파일을 덮지 않도록 읽기 사본과 작성 정본 구별 |

심판 한 회는 다음을 명시해야 한다.

1. 시작 시 현재 자격을 읽고, 재시작이면 기존 assign·locks·신청·허가 이력·미처리 신호·outbox를 복구한 뒤 새 허가를 시작한다.
2. 변경 감지는 최적화로만 쓴다. 목록 읽기 실패·내용 받기 실패는 ‘없음’이 아니다. 마지막으로 완전히 읽은 버전과 미처리 항목을 유지한다.
3. 기존 1단계 목록에 ULD heartbeat/반납, outbox/ack, 운영 버전·routing 변경을 포함한다. 자격·시간 경과 만료는 파일 변경이 없어도 다시 판단한다.
4. 확정 시작의 승인과 끝·반납·확인·ready·outbox 적용 결과를 먼저 반영한 뒤 만료를 판단한다. 확정 여부가 불명확하면 재허가하지 않는다.
5. 다중 자원과 묶음 판정을 decision ID로 묶고 부분 게시를 실행 허가로 보지 않는다. 남은 작업·회차 cursor를 저장하고 20초가 지나도 이미 보낸 전송이 계속되지 않도록 처리한다.
6. 소비 확인은 판정/실행 효과가 확정된 뒤 한다. `OWNER_READY`는 어떤 임대 gen에 대한 응답인지 포함해야 하며 구임대 ready로 새 임대를 활성화하면 안 된다.
7. 마지막 heartbeat는 심판 자체가 갱신해야 한다. 작업 프로세스 heartbeat가 살아 있다는 이유만으로 멈춘 심판을 살아 있다고 판단하지 않는다.

|---|---|---|

| shape | before export→함수 안 추론·batch 업로드 또는 일괄 교체→이름/after export→history | 2판의 분리 방향은 맞음. 아래 보호 조건을 보존해야 함 |

| 백업·export | CVAT 준비 요청→대기 CSV 기록→수신/재사용 복사→manifest·파일 게시 | 준비 단계에도 공유 CSV 기록은 있음. 제어 기록을 세션 단일 작성으로 정의하고, 산출물과 완료 근거의 게시 뒤에만 요청 결과 반영 |
| 데이터셋 | 모델 잠금→zip 선택·변환·출처/서명·zip/json/report→학습 | 준비 중 모델 폴더를 만들거나 결과를 지우는 기존 부분 제거. 고정 시험 설정의 내용·gen을 한 번에 읽어 변환과 출처에 같은 사본 사용 |

| 초기화·정리 | 실제 삭제와 정리 이력 | 모델 외 데이터셋 참조 보호, tombstone 독자 제외가 필요(E9·E13) |

`auto_annotate_frames`를 나눌 때 보존할 동작:

- **사람 라벨 보호:** 요청 접수 당시가 아니라 올리기 직전 최신 이름·라벨 수를 확인한다. `AA_EXISTING`/`ALLOW_REPLACE`/대상 `_uld`·`_AA` 예외의 의미를 유지하고, 잠금 허가 자체를 교체 동의로 해석하지 않는다.
- **직전 백업:** 추론 전에 받은 기준 라벨과 확정 직전 백업을 구별한다. 후자는 수신·무결성·복구 가능한 게시를 확인한 다음 첫 CVAT 쓰기를 허용한다.
- **실제 올릴 결과의 출처:** 로컬 결과에 TASK/서버, 프레임 매핑·삭제 프레임, 라벨 이름·모델 지문·설정을 남긴다. 허가 대기 중 CVAT 메타가 바뀌었으면 라벨 ID를 재연결하고 호환되지 않으면 재준비한다.
- **교체·덧붙임:** 기존 함수는 replace일 때 전체 프레임 제한을 검사하고 500개씩 쓰며, 비교체는 50프레임마다 쓴다. 분리 후에도 부분 프레임 교체를 허용하지 않는다. 덧붙임 실패는 ‘복원됨’으로 단정하지 않고 부분 반영을 표시한다.
- **복원 결과:** 현재 `replace_annotations`는 복원 성공/실패를 로그로만 남기고 원래 오류를 다시 던진다. `실패(복원됨)`을 확정하려면 복원 결과를 구조화해 전달하고 검증해야 한다. 최초 `remove_annotations()`도 try 밖에 있으므로 예외가 났다고 무변경이라고 단정하면 안 된다.
- **취소·기록:** 로컬 추론 중 취소는 CVAT 무변경, 확정 승인 이후 취소는 현재 TASK 마무리로 연결한다. `replaced`, frames·boxes·quality·누락 프레임 반환값과 `label_uploaded`, before/after counts·업로드 로그·history를 보존한다. 종료 로그가 아니라 사전 기대 결과와 작업 식별자를 복구 근거로 남긴다.

이들은 현재 코드가 설계와 다르다는 사실을 새 미구현 버그로 센 것이 아니라, 명시된 분리를 구현할 때 깨지지 않아야 할 조건이다.

## 5. 한도·운영 전환과 검증

- Apps Script의 부담을 CPU로 옮기는 방향은 타당하다. 다만 Keeper가 ‘할 일이 있음’을 요청 폴더 목록으로 판단하면 30일 보관한 완료 요청도 이름은 매번 읽게 된다. 미배정 pending·사람 잠금 신청·격리 확인·outbox 복구 등 깨울 조건을 구분해야 한다. U2 2초 목표는 실측 전 보장할 수 없다.
- 심판의 20초 예산은 6개 이상 폴더 목록·변경 본문·여러 판정 쓰기와 10분 전수 읽기를 포함한다. cursor 없이 매번 처음부터 읽다가 시간 한도에 닿으면 뒤 파일이 계속 밀릴 수 있다. 폴더 수정 시각 목록의 실제 소요 시간은 요청서대로 별도 실측 사항이다.
- 마스터의 현재 밤 종료·MAX_RUN_HOURS 종료는 1185행 이후 루프에 있다. 심판이 종료돼도 허가받은 작업은 계속될 수 있으므로 정상 반납·확정 중 표시·후임 복구를 남겨야 한다. Keeper가 승인된 야간 일과 정지 hold를 어떻게 존중하는지도 정의해야 한다.
- `min_version`은 새 코드의 협조 규칙이다. 이를 모르는 v4.32.0 세션을 막아 주지 않으므로 전환 ①에는 사람 셀·GPU·기존 Apps Script 트리거·백그라운드 업로드까지 종료 확인이 필요하다. 확정 중인 CVAT 작업은 E2의 종결 확인 대상이다.
- versions 비교는 문자열 사전순이 아니라 파싱된 버전/프로토콜 버전으로 정한다. 최소 버전 파일을 읽지 못하면 공유 쓰기는 보류한다. 패키지·노트북 사본·마스터가 함께 맞는지도 확인해야 한다.

이번에 실행한 확인은 `/tmp/egg_b1_probes.py`에 있다. 네트워크 없이 실제 v4.32.0 함수로 두 경우를 확인했다.

| 확인 | 결과 | 의미 |
|---|---|---|
| 동일 SESSION_ID에서 `write_sharded` 두 줄이 같은 PID 임시 파일에 쓰고 replace 직전 만나게 함 | 하나는 FileNotFoundError, 하나는 성공 반환. 최종 파일은 성공 반환 줄이 요청한 TASK와 달랐음 | E5. 현재 공용 함수를 줄별 폴더 선언만으로 병렬화하면 안 됨 |
| pending A 설정→해제→지연된 A 설정 재적용 | `track_pending={'xml':'A.xml'}`로 복귀 | E3. mutation 재생은 gen 이력 확인 외에 적용 ID·순서가 필요함 |

첫 확인은 `write_sharded`가 checked_time을 처리하지 않는 최소 열 목록으로 실행했으며 `os.replace` 직전에 barrier를 주었다. 실제 Drive 지연 시험이 아니다. 둘째는 새 outbox 구현 시험이 아니라 현재 mutation의 비가환성을 확인한 것이다. 기존 회귀 시험 전체나 새 심판 코드의 시험은 실행하지 않았다.

## 점검했지만 문제가 없던 항목

- CPU 심판과 Apps Script 자격 발급을 나누는 역할 자체는 비밀 값 저장·웹앱 배포 금지 약속을 바꿀 필요가 없다. Keeper에는 CVAT 토큰이 필요하지 않다.
- 모델 잠금을 모델 폴더 밖으로 이동하고 초기화·복원·정리도 같은 자원으로 보는 결정은 D3의 기존 삭제 틈을 직접 다룬다.
- 준비 산출물 임시화·자동 라벨 함수 분리·게시 단계 도입은 D2·D4의 원인과 맞는다.
- 설정 잠금과 sim 세션 결과, 생성 뒤 불변 데이터셋·고유 zip 이름은 기존 전체 파일 덮어쓰기 범위를 줄인다.
- 취소 신호·실행 기본값의 assign 이동·노트북 자동 요청 생성자·야간 승인 직렬화는 D14에 대응한다.
- ULD가 자기 폴더에 반납·생존 신호를 쓰고 우리는 읽기만 하는 규칙은 약속 5와 양립한다. 실제 소비 누락은 E7이다.
- 백업 prune 폐지·기존 목적지 삭제 없는 다운로드·자율 RUNNING 해제 제거·일반 원격 삭제 금지는 1판 삭제 목록의 주요 누락을 반영했다.
- 16번은 새로 복원한 TASK의 꼬리표를 다루므로 기존 TASK 임의 개명 금지의 허용 예외를 유지할 수 있다.

## 시간이 모자라 보지 못한 항목 및 검증 한계

- 2판의 여섯 검토 질문과 D1~D14 판정은 모두 다뤘다. 기존 전체 체크리스트의 재전수 리뷰나 모든 셀의 실행 시험은 아니다.
- 새 Arbiter·Keeper·34번 셀·outbox 구현이 없으므로 설계에서 정하지 않은 부분은 실행 실패를 관찰했다는 뜻이 아니다. 확신란의 ‘확인함’은 설계·코드 순서 대조 또는 명시된 로컬 함수 확인에 한정된다.
- 실제 Drive 권한·지연·Apps Script 실행 시간·Kaggle 세션 한도는 측정하지 않았다. 외부 정책의 현재 수치도 조회하지 않았다.
- 실제 CVAT 비동기 작업 종결·라벨 정규화 비교·복원 성공 검증과 GPU 추론/에폭 취소는 실행하지 않았다.
- 저장소 밖 LC앱·AA앱·ULD앱 코드는 검토하지 않았다. F7·F8은 판정하지 않았으며 묶음과 자원 권한이 겹치는 범위만 다뤘다.
