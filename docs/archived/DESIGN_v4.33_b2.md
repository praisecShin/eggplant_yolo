# 가지 앱 경합 통제 설계표 3판 (v4.33)

2026-11-14 · 재웅님 · 2판 검토(E1~E14)와 11/14 결정을 반영해 단순화

사람(M)은 여럿이 동시에 일합니다. 대신 CVAT와 공유 파일을 바꾸는 일은 **배정받은 실행기만** 합니다. 사람은 앱으로 요청하고, 노트북 셀로는 분석(CVAT 읽기, 자기 분석 폴더에 쓰기)만 합니다. 판정은 CPU 마스터 한 곳이 하고, 자동으로 판단하기 어려운 복구는 사람에게 '확인 필요'로 넘깁니다.

## 심판: CPU 마스터

| 부분 | 하는 일 | 규칙 |
| --- | --- | --- |
| 판정 루프 (주 스레드) | 20~30초마다 한 회 (아래 순서) | CVAT를 부르지 않음. 제어 파일 전용 rclone 경로, 명령마다 timeout. 큰 전송과 잠금을 함께 쓰지 않음 (E6) |
| 생존 신호 스레드 | 60초마다 `workers/<마스터>.json`·`jobs/ARBITER.json` | 판정 루프가 마지막으로 끝난 회차를 적음. 판정 루프가 멈추면 ARBITER의 회차가 멈춰 Keeper가 알 수 있음 |
| CPU 작업 프로세스 | 백업·export·받는 중 확인·상태 갱신(취합 일)·관리 일 중 CPU 일 | 마스터가 `python -m worker_cpu`로 띄우는 별도 프로세스. 전역 설정·rclone 잠금을 마스터와 함께 쓰지 않음. 다른 실행기와 같은 규칙 (E5) |

판정 루프 한 회:

1. **자격 확인:** `ARBITER_GRANT.json`의 세션·epoch가 내 것인지. 아니면 판정을 멈추고 작업 프로세스에 새 일을 주지 않음.
2. **입력 읽기:** 요청 폴더 2개, `locks/ask/`, `workers/`, `jobs/signals/`, `CVAT_UpLoader/requests`·`locks_ask`·`workers`, `config/min_version.json`·`routing.json`. 수정 시각 목록으로 바뀐 것만 읽고 10분마다 전체를 읽음. **목록이나 내용을 못 읽으면 '없음'이 아니라 '모름'**으로 두고 그 대상의 회수·허가를 미룸.
3. **보고 반영:** 확정 신청·확정 끝·반납·결과 보고를 먼저 반영.
4. **만료:** 생존 신호가 3분 끊긴 실행기 — 확정 승인 전이면 회수·재배정, 확정 승인 뒤면 '확인 필요'로 격리.
5. **신호·취소:** 마스터가 받는 신호(정지·해제·승인·취소·확인 결과)를 도착 순서대로 처리하고 결과를 `jobs/ARBITER.json`에 적음.
6. **배정·허가:** 차례에 따라 요청 묶음·TASK 잠금·관리 일을 정함. 한 판정은 decision ID 하나로 묶어 `assign/`에 먼저 쓰고, 잠금 파일에는 같은 decision ID를 적음. 실행기는 둘이 맞을 때만 시작.
7. **확정 승인:** 확정 신청이 온 TASK에 승인(decision ID·gen·시각)을 적음.
8. **회차 기록:** `jobs/ARBITER.json`에 epoch·회차·시각·처리 수·이번 회 '모름' 목록.

모든 판정 파일에는 심판 epoch와 대상 gen을 함께 적습니다. 실행기는 현재 자격 epoch의 판정만 따릅니다 (E4).

재시작 복구: 새 마스터는 자격을 받은 뒤 첫 회에 전체를 읽고, 이전 epoch의 `assign/`·`locks/`를 그대로 이어받습니다. 확정 승인이 있는데 확정 끝이 없는 TASK는 '확인 필요'로 둡니다.

심판 자격:

- 마스터는 켜지면 `jobs/arbiter_ask/<S>.json`을 씁니다.
- Keeper(U2)는 1분마다 확인하고, LockService 안에서 살아 있는 심판이 없을 때만 `ARBITER_GRANT.json`(세션·epoch +1)을 씁니다. '살아 있음'은 ARBITER의 판정 회차가 3분 안에 올랐는지로 봅니다.
- 자격을 잃은 옛 마스터가 늦게 쓴 판정은 epoch가 낮아 실행기가 따르지 않습니다.

## 실행기 규칙

TASK 하나를 처리하는 순서:

| 단계 | 하는 곳 | 심판과의 관계 |
| --- | --- | --- |
| 1. 받기·추론·track 만들기 (TASK 전체를 로컬에서 끝까지) | 세션 임시 폴더 | 배정·잠금 확인 |
| 2. 확정 직전 다시 검사: TASK 이름·기존 라벨 수·사람 라벨 보호 설정 | CVAT 읽기 | — |
| 3. **확정 신청** | `locks/ask/<S>__<자원>.json`에 '확정 신청' | 심판이 다음 회에 승인 (최대 20~30초) |
| 4. 승인 확인 뒤 올리기 전 백업 | Drive 게시 | 승인의 decision ID·gen 확인 |
| 5. 교체·올리기, 실패하면 백업으로 복원 | CVAT | — |
| 6. 이름 바꾸기 (`_uld` → `_uld_AA`) | CVAT | — |
| 7. 산출물 게시·TASK 기록 | Drive | 실패하면 그 자리에서 다시 시도 (최대 10분) |
| 8. 확정 끝·결과 보고·반납 | `locks/ask/` | 심판이 다음 회에 풀어 줌 |

- 확정 신청부터 확정 끝까지 실행기는 다른 일을 하지 않고, 생존 신호를 계속 보냅니다.
- 7단계를 10분 안에 끝내지 못하거나 확정 중에 끊기면 그 TASK는 '확인 필요'입니다. 자동으로 다시 하지 않습니다 (E2·E3).
- 실행기 안의 병렬 줄(30번 셀의 GPU·입출력 줄)은 서로 다른 TASK만 맡습니다. 줄마다 CVAT 접속·작업 설정 객체·세션 기록 파일을 따로 씁니다 (E5).
- 자동 라벨 함수(`auto_annotate_frames`)는 '로컬 완성'과 '올리기'로 나눕니다. 올리기 쪽은 교체 때 전체 프레임 검사, 500개씩 쓰기, 실패 시 복원 결과를 구조화해 돌려줌(성공·실패를 결과에 남김)을 지킵니다.

## '확인 필요' 처리

| 원인 | 앱에 보이는 것 | 사람이 고르는 것 |
| --- | --- | --- |
| 확정 중 실행기 끊김 | TASK, 어느 단계였는지, 올리기 전 백업 위치, 올리려던 결과 위치 | ① 정상 (CVAT가 올리려던 결과와 같음) ② 백업으로 되돌리기 요청 ③ 다시 하기 요청 |
| 복원 실패 | 위와 같음 + 오류 | ② 또는 ③ |
| 기록 게시 실패 | TASK, 남은 기록 | ① (기록만 다시 게시하는 요청) |

- 3단계 확정 신청 때 '올리려는 결과 파일 위치와 백업 위치'를 함께 적어 두어, 확인할 자료가 항상 Drive에 있게 합니다.
- 사람이 고르면 확인 결과 신호가 가고, 심판이 그 TASK 잠금을 풀어 줍니다. 그 전까지 그 TASK는 아무에게도 배정되지 않습니다.

## 관리 일

학습, 학습 초기화(FORCE_NEW), 데이터셋 만들기, 학습 복원(23번), 모델 정리(29번), 시험 TASK 바꾸기(33번), 청소(34번)는 '관리 일'입니다.

- 관리 일은 전체에서 **한 번에 하나**만 실행합니다. 모델·데이터셋을 함께 쓰는 일끼리 서로 기다리다 멈추는 일(E8)과 학습이 읽는 데이터셋을 정리가 지우는 일(E9)이 없어집니다.
- 학습은 오래 걸리므로, 학습 중에는 데이터셋 만들기·정리가 학습이 끝날 때까지 기다립니다.
- 학습은 시작할 때 쓴 데이터셋 이름·서명·시험 TASK 설정 gen을 학습 출처에 남깁니다.
- 초기화한 옛 모델 폴더는 `trash/runs/<모델>__<시각>/`으로 옮깁니다. `runs/` 밖이라 모델 목록에 다시 나오지 않습니다 (E13).

## 차례

- **TASK마다:** 접수 순서(LC·AA 두 폴더를 합친 순서). 앞 요청이 기다리는 TASK는 뒤 요청이 먼저 잡지 않습니다.
- **사람마다:** 묶음 단위로 돌아가며. 한 요청은 5개 TASK 묶음(`W_CHUNK_TASKS = 5`)씩 받습니다.
- **30분 한도(`W_CHUNK_MIN = 30`):** 새 TASK를 시작하지 않는 부드러운 경계입니다. 진행 중인 TASK는 끝냅니다 (E11).
- **묶음이 끝나면:** 실행기가 반납을 보고하고, 심판이 반납을 반영한 뒤에 다음 차례를 정합니다.
- **백업·export의 '받는 중':** TASK 잠금을 잡지 않고 묶음 자리도 차지하지 않습니다. 받은 파일을 게시할 때만 그 TASK 잠금을 잡습니다.
- **TASK로 나눌 수 없는 일:** 학습 같은 관리 일은 묶음 없이 하나로 처리합니다.

| 스냅숏 요약: `web/snapshots.json` | 취합 일 (위 TASK 단위 목록을 모아 만듦) (E12) |
| `relabel/tasks/<id>.json`, `tasks/<id>/**`, `relabel/previews/<id>*`, `backups/<기본이름>/**` | 그 TASK 잠금을 가진 실행기 |
| `runs/<모델>/**`, `datasets/**`, `config/test_tasks.json`, `trash/**` | 관리 일을 맡은 실행기 |
| `analysis/<M>/**` | 그 사람 M의 세션 |
| `workers/<S>.json`, `logs/shards/<이름>/<S>[_<줄>].csv` | 세션 S (줄마다 따로) |
| `backup_status.csv`, 작업보드 | 백업을 실행한 실행기 (파생 파일 예외) |
| `status/*` (`cvat_tasks.json`, `changes*`, `collector.json`, `auto_requests.json`, `requests.json` = CVAT 준비 상태) | 수집기 (E14) |
| `config/people.json`, `config/routing.json`, `config/min_version.json` | 관리자 사람 (M1) |
| `CVAT_UpLoader/**` | ULD앱 (우리는 읽기만) |

- `status/dispatcher.json`(배정기 상태)는 Apps Script에서 빼고, 같은 내용을 `jobs/ARBITER.json`에 둡니다.

## 신호

- 신호는 매번 새 이름으로 만듭니다. 받는 곳은 마스터 하나입니다 (E10).
- 마스터는 도착 순서(자기가 목록에서 처음 본 순서)로 처리하고, 처리 번호와 결과를 `jobs/ARBITER.json`의 신호 장부에 적습니다. 새 마스터는 이 장부를 이어받아 같은 신호를 두 번 처리하지 않습니다.
- 해제 신호는 어느 정지 신호를 푸는지 ID로 적습니다. 지금의 `until` 보류, 수동 깨우기, 마스터가 멈출 때 GPU도 멈춤의 의미는 그대로 둡니다.
- GPU 작업자에게 멈추라고 할 때는 마스터가 그 작업자의 배정에 '멈춤'을 적습니다. 작업자는 자기 배정을 보고 멈춥니다.

## 지움 표시와 청소

- 요청 상태 바뀜은 이름 바꾸기 하나로 합니다. 옛 이름 지우기가 없습니다.
- 신호·확정 표시·생존 신호는 지우지 않고 남깁니다. 청소(관리 일)가 기간이 지난 것을 정리합니다.
- 백업 오래된 작업본 정리(`prune_work`)는 없앱니다. 다시 받을 때 기존 파일을 지우지 않고 새 이름으로 받습니다.
- 0번 셀 자동 동기화는 원격 삭제를 하지 않습니다. 분석 모드에서는 자기 분석 폴더만 올립니다.
- 청소(34번, 관리 일): 미리 보기 → 표시 뒤 7일, 끝난 요청 30일, `trash/` 30일이 지난 것만 지움. 소유자가 달라 못 지운 것은 계정별 목록으로 보여 줌.
- 절대 지우지 않는 것: `CVAT_UpLoader/`, `videos/`, `backups/`, `exports/`의 zip, CVAT TASK. 가중치·데이터셋은 29번 모델 정리(관리 일)만.

## ULD앱

- 교체는 우리 앱에 '교체 신청'을 냅니다(자기 폴더 `CVAT_UpLoader/requests`). 심판이 TASK 잠금을 ULD 세션에 허가하면, ULD는 확정 신청·승인 절차를 거쳐 교체합니다.
- ULD의 신청·반납·생존 신호는 ULD 자기 폴더(`CVAT_UpLoader/locks_ask/`, `CVAT_UpLoader/workers/`)에 쓰고, 심판이 2단계에서 읽습니다.
- 중복 검사는 TASK 번호로 합니다.

## 운영 전환

1. 모든 실행을 멈춥니다: 작업자·마스터·GPU 작업자, 사람이 켠 노트북 세션, 기존 Apps Script 트리거, 진행 중인 업로드.
2. scripts·노트북·Apps Script를 반영하고 `config/min_version.json`을 올립니다. 버전은 숫자로 비교합니다.
3. 마스터를 켜 자격을 받습니다. 옛 세션이 받아 둔 요청은 재배정되고, 확정 중이던 것은 '확인 필요'로 둡니다.
4. 작업자를 켭니다. 최소 버전보다 낮은 세션과 최소 버전 파일을 못 읽은 세션은 공유 쓰기를 하지 않습니다.

## 정할 것과 먼저 시험할 것

- [ ] 공유 폴더 권한: 다른 계정이 만든 파일의 이름 바꾸기·덮어쓰기·지우기
- [ ] Keeper 한 회 실행 시간 (2초 이내인지)
- [ ] CPU 마스터에서 제어 폴더 목록(수정 시각 포함) 한 번의 시간

정할 것 (괄호 안은 제안):

1. 사람 목록 (`config/people.json`).
2. 관리 일을 전체 하나로 할지 (제안: 하나. 학습이 둘 이상 동시에 필요하면 다시 논의).
