## 검토 질문

### A. R1~R7

1. R1~R7이 해결됐는지 판정해 주세요. b12 재현 스크립트(`/tmp/egg_b12_probes.py`, `/tmp/egg_b12_keeper_probes.js`, `/tmp/egg_b12_beat_probe.py`)가 남아 있으면 다시 돌려 주세요. Keeper 재현은 입력에 `holds`가 필요해졌습니다(b12 1절).
2. **R1:** `input_problem`이 확인하는 칸이 실제로 판정 함수가 쓰는 칸을 덮는지 봐 주세요. 확인하지 않는 칸 하나로 회차 전체가 실패하는 경로가 아직 있으면 짚어 주세요. 반대로 너무 엄격해서 앱·실행기가 정상으로 쓰는 파일을 버리는 경우가 있는지도 봐 주세요.
3. **R2:** Keeper가 정지 신호를 무시하는 기준(소유 계정이 `release` 권한이 있는 등록된 사람)이 심판의 기준(`PERM_OF_SIGNAL["stop"]`)과 같은지 봐 주세요. 사람 목록을 못 읽을 때 모두 보류로 보는 선택이 다시 R2와 같은 막힘을 만드는지 의견을 주세요(이때는 '사람 목록 모름' 메일이 나갑니다).
4. **R3:** '기록 있음·못 읽음'과 '기록 없음'의 구분이 목록 실패까지 덮는지 봐 주세요. 목록(`getFiles`) 자체가 실패하면 Keeper 한 회 전체가 예외로 끝나고 아무것도 쓰지 않는다고 보았습니다.
5. **R7:** 생존 신호 스레드가 `join_timeout` 안에 끝나지 않으면 주 스레드는 '끝남'을 쓰지 않습니다. 이때 3분 뒤 생존 신호가 끊긴 것으로 정리된다는 설계가 받아들일 만한지 봐 주세요.

### B. 배포 계획 2판

6. 6절 '막기 → 비우기 → 대장 → 사본 → 켜기'와 되돌리기 대조가 b12 R4의 반례(옛 실행기가 CVAT 가져오기를 접수하고 요청 완료 전에 꺼짐, 전환 뒤 옛 '받음' 요청을 새 방식이 처리한 뒤 되돌림)를 막는지 봐 주세요. 심판이 `pending`만 접수하는 코드 변경도 함께 봐 주세요.
7. 7절 ULD 손 절차가 R5의 조건(확정 승인 상태·서버 가져오기 진행 중)을 덮는지 봐 주세요.
8. 8절 예행 연습(같은 계정, `_test` 폴더·노트북, CVAT 프로젝트 `eggplant_AA`, `REH_` TASK만, G에만 시험용 Apps Script 둘)에서 운영과 섞일 수 있는 경로를 찾아 주세요. 예: 운영 수집기가 시험 TASK를 봄(T12), 같은 Kaggle 키, 같은 CVAT 토큰, 같은 메일 주소.
