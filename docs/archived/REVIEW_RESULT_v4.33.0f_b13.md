## 요청한 경계에 대한 의견

- **R1 엄격성:** 현재 공식 앱 형식과 실행기가 쓰는 session/fp/caps, 숫자 epoch/gen/chunk, 문자열 TASK·이름은 통과한다. 정상 생성 파일을 잘못 버리는 확정 반례는 이번 범위에서 찾지 못했다. 다만 scalar라는 조건은 ‘실제로 안전하게 사용 가능’과 같지 않다(S1). 모든 필드의 스키마를 전수 증명한 것은 아니다.
- **R2 사람 목록 모름:** stop이 있으면 기동이 막힐 수 있으나, 알 수 없는 권한을 허용하지 않는 명시된 안전 선택이다. 목록 읽기 회복 후 다시 판단하므로 과거의 ‘알려진 무권한 stop 하나로 무기한 막힘’과 구분된다. 장기 장애에는 메일을 받은 관리자가 목록 접근을 복구해야 한다. 정상 people 스키마에서는 심판과 일치하나 status=null/빈 문자열 같은 잘못된 설정은 Keeper의 falsy 허용과 심판의 정확한 active 비교가 다르므로 설정 검증·표현 통일이 바람직하다.
- **R3 목록 실패:** getFiles 실패는 입력 구성 중 예외로 빠져 grant·해제·깨우기·wake_done 상태 쓰기에 도달하지 않는다. 그 전에 jobs/wake_done 폴더가 없으면 폴더 생성은 가능하므로 ‘아무것도 쓰지 않음’은 판정 결과 파일에 대한 설명으로 한정한다. 이번 재현은 기존 폴더에서 수행했다.
- **R7 join timeout:** 종료 표시가 없더라도 마지막 성공 heartbeat 이후 3분이 지나면 정리되는 선택은 받아들일 만하다. 지연 중이던 쓰기가 나중에 성공하면 저장소 수정 시각이 아니라 그 heartbeat 안의 hb 시각으로 만료를 판단한다. 단, 영구 정지는 별도 진행 감시로 다룬다는 2단계 조건을 유지해야 한다.
- **전환·ULD:** 완료 기록 전에 꺼진 옛 실행은 CVAT 실제 효과 대조 후 transition으로 격리하고 남은 TASK만 새 요청으로 낸다. 새 방식 처리 후 롤백도 결과·CVAT 대조 뒤 완료분을 빼므로 b12의 두 반례를 막는 절차가 갖춰졌다. 서버 가져오기 여부가 모르면 ‘없음’으로 취급하지 말고 전환/교체를 미뤄야 한다. 실제 도구 구현의 검증은 이후 필요하다.
- **시험 환경 혼입:** T12의 운영 프로젝트 제한, 시험 수집기·심판의 프로젝트+REH_ TASK 제한, 별도 Drive remote와 Kaggle slug는 필요한 분리다. 2단계에서는 요청 TASK ID를 직접 넣은 경우도 시험 범위 밖 쓰기를 거절해야 한다. 같은 Kaggle 키·CVAT 토큰 사용 자체는 혼입이 아니지만 운영 권한을 그대로 갖는다. 키 재발급·토큰 폐기는 운영도 바꾸므로 예행 연습에 포함하지 말고, 기동 대상 slug와 실제 프로젝트/TASK를 쓰기 전에 확인해야 한다. 같은 메일은 `[시험]` 표지로 구분하고 Kaggle 자원 한도 공유는 문서대로 관리한다. 아직 없는 연결 코드를 검증 완료로 보지는 않았다.

## 2단계 전 최소 목록

1. S1을 수정하고 잘못된 요청 옆의 정상 요청 진행 시험을 추가한다.
2. S2·S3을 문서와 전환 정리 도구 요구사항에 반영한다. 도구를 구현하기 전 또는 예행 연습 전에 끝내야 한다.
3. 이후 2단계 개발 진행 가능. 진행 감시·CVAT 시간 한도·manifest 최종 검증·시험 범위 강제·전환 대장 도구는 기존 계획대로 운영 연결 전 필수 검증 대상으로 유지한다.

## 점검했지만 문제가 없던 항목

- pending만 새 접수, 전환 확인 필요 요청 점검, 야간 승인 실행기 대기의 시간대 전환 처리.

## 시간이 모자라 보지 못한 항목·한계

- 전체 입력 필드 퍼징, 모든 읽기/쓰기 중단 조합과 기존 v4.32 전체 회귀 시험은 수행하지 않았다.
- 실제 Drive·CVAT·Kaggle·Apps Script와 미구현 2단계 연결은 검증하지 않았다. 검토 결과는 이번 수정 범위의 가짜 환경 시험·코드·문서 추적에 한정한다.
