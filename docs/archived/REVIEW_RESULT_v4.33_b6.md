| 칸 | 내용 |
|---|---|
| 번호 | K6 |
| 심각도 | 높음 |
| 관점 | 복구·동시성 |
| 관련 항목 | 약속 7, J7, 새 TASK 응답 유실 복구 |
| 위치 | 설계 348~355행; 점검표 90행; 16번 75~90행, 17번 81~95행 |
| 무엇이 문제인가 | 후보가 정확히 하나라는 것만으로 해당 생성 의도의 결과임을 증명하지 못한다. 새 TASK 번호가 없을 때 동일 이름/계정의 생성 요청을 직렬화하거나 원본·서버 작업과 연결하는 조건이 없다. 기존 코드도 같은 이름을 금지하지 않는다. |

| 제안 | 서버 작업 ID가 있으면 의도와 연결하고, 없으면 계정·서버·동명 생성에 대한 예약과 원본/프레임 수·라벨·미디어 등 결과 검증을 둔다. 하나뿐이어도 출처를 증명 못 하면 확인 필요로 둔다. 묶음 생성은 요청 ID 아래 작업별 의도/결과를 분리해 intent 하나를 덮어쓰지 않는다. |

## 3. 새 장치별 나머지 점검

- **버전·채택:** 실행기 산출물과 심판의 CURRENT를 분리해 J2/J5의 본래 반례는 닫힌다. 23번·FORCE_NEW는 학습 시작 가중치를 바꾸지 않고, 모델의 채택 gen이 바뀌면 학습 결과를 채택 대기로 두는 방향도 맞다. 바뀜 검사는 버전 문자열만이 아니라 채택 gen으로 해야 A→B→A도 인식한다.
- **읽기 참조·청소:** ‘참조 중/채택 버전은 삭제 안 함’과 확인 필요·채택 대기 보존이 명시됐다. 구현은 심판의 버전 참조 등록과 청소 대상 확정의 순서를 정해, CURRENT 읽기→참조 등록 사이 또는 오래된 청소 계획 뒤에 새 참조가 생기는 경우를 시험해야 한다. 단순 폴더 스캔/heartbeat 부재만으로 참조가 없다고 판단하면 안 된다. 명시된 보존 조건을 구현하는 사항으로 보고 별도 결함을 추가 집계하지 않았다.
- **legacy 등록:** 목록만 만들고 원본을 옮기지 않는 방식은 가능하다. 목록이 버전 디렉터리 밖 기존 파일을 가리키는 표현과 경로 허용 범위를 정의하고, 청소는 목록에 연결된 자산만 지워야 한다. 모델·데이터셋·시험 설정을 모두 한 번 등록하고, 파일을 지우거나 기존 학습을 재실행하지 않는 전환 시험이 필요하다. 설계 운영 전환 1~4단계에는 legacy 등록의 삽입 위치가 빠져 있고 점검표 78행에만 있으므로 시작 전 마이그레이션 단계로 넣어야 한다.
- **학습 줄:** 다른 모델은 병렬, 같은 모델은 직렬이고 관리 확인 필요는 학습 전부를 막지 않는다. 기존 0번 학습 callback(934~963행)의 에폭별 Drive 게시와 DDP 별도 프로세스는 실행별 버전 경로로 바꿔야 한다. 완료 목록을 게시하기 전에 background push가 모두 끝났는지, 목록 뒤 버전 파일이 더 변하지 않는지를 시험한다. 시험 설정 충돌은 K5로 분리했다.
- **관리 일 비켜 두기:** 실행기 없는 요청을 제외한 FIFO로 해석하면 새 교착은 발견하지 못했다. 실행기가 돌아오면 원접수 순서상 앞인 비켜 둔 일부터 다음 차례를 주고 현재 관리 일을 선점하지 않는 시험이 필요하다. 여러 비켜 둔 일이 있을 때도 원접수 순서를 보존한다.
- **Keeper 시도 ID:** 제한 재시도는 모르는 외부 효과에 대한 정책을 명시한다. 한 번 더 push해도 이전 시도가 뒤늦게 시작할 가능성은 남으므로 단일 심판 자격으로 중복 프로세스의 판정을 제한해야 한다. 재시도 때도 최신 보류·권한·STOP ID를 검사하고, 처리 중 상태는 완료 파일 존재만으로 건너뛰지 않는 시험이 필요하다.
- **실행 코드:** 기존 `load_script`(0번 871행 이후), `_lc_run`(30번 1040행 부근), Python/subprocess 진입점도 검증된 같은 바이트를 실행해야 한다. CPU 마스터 `start_gpu_worker_if_needed`(532~557행)는 기존 `notebooks/`에서 GPU 노트북을 고르므로, 이 경로도 deploy의 승인된 GPU 노트북/metadata를 쓰도록 점검표에 명시한다. 선언상 ‘실행 코드 전부’에 포함되지만 현재 점검표는 마스터/import 중심이다.
- **사후 annotation 비교:** export zip/XML의 파일 해시와 추론 결과의 파일 해시는 생성 시각·파일 형식·정렬·좌표 표현 때문에 의미상 같아도 다를 수 있다. 복구 자료의 바이트 무결성 해시와 원격 annotation의 정규화된 내용 비교를 나누고, shape·track·덧붙임 각각의 기대 최종 상태를 시험해야 한다.

## 5. 구현 착수 판단

### 구현 전에 설계를 고쳐야 할 것 — 최소 목록

1. **신호의 효과별 복구 의미(K1):** gen 불일치와 효과 완료를 구분하고 부분 효과를 이어갈 기준을 정한다. 점검표 74행의 옛 재생 규칙을 현재 규칙과 통일한다.
2. **배포의 비순환 신뢰 사슬(K2):** 루트 노트북과 의존 목록의 해시 범위를 정한다.
3. **생산자와 요청자 연결(K3):** 사용자·대리 앱·U1/U2·심판·실행기의 입력 권한과 최초 신원 보존 규칙을 정한다.
4. **깨우기 시간/관측 경계(K4):** next_wake_at과 관측 워터마크를 Keeper가 어떻게 쓰는지 정한다.
5. **시험 설정 변경의 호환성(K5), 새 생성 결과 식별(K6):** 기존 학습/데이터셋이 새 시험에 유효한지와 응답 유실 TASK가 해당 의도의 결과인지 확인할 기준을 정한다.

독립 판정 함수·가짜 Drive/CVAT·접근 컨텍스트 뼈대는 먼저 구현할 수 있다. 위 규칙을 구현자의 임의 선택으로 남긴 채 여러 실행기/앱의 공용 프로토콜을 확정하거나 운영 전환하는 것은 권하지 않는다.

### 구현하면서 시험으로 확인하면 되는 것 — 점검표에 넣을 항목

- 신호 계획만 저장/효과 일부 저장/새 epoch 재배정 직후 장애에서 **필요한 효과가 빠지지 않고 최신 상태도 돌아가지 않음**.
- 실제 최종 배포 바이트로 비순환 해시 검증, GPU 노트북·동적 load_script·subprocess 변조 거절, 검증한 파일과 실행한 파일 동일성.
- U2 해제·심판 복구·대리 앱 생성·다른 자격 실행기의 상태 변경 후에도 원요청자와 권한이 맞음.
- count=0으로 종료한 뒤 next_check 도래, 목록 읽기와 회차 게시 사이 새 요청, 야간/아침 전환, 실행기 재등장.
- 모델 CURRENT가 A→B→A인 경우 채택 대기, 시험 T0→T1 뒤 모델/데이터셋 호환 판정, 보류된 학습 버전 보존.
- 청소 계획 뒤 새 참조 등록/채택, 참조 상태를 못 읽는 경우 삭제 보류, legacy 원본 보존 및 목록 경로 해석.
- 학습 background push 종료 후 목록 확정, 버전 파일 불변, FORCE_NEW·복원·정리 중 학습 입력 해시 유지.
- 같은 이름의 동시 생성·서로 다른 원본·생성 뒤 suffix 변경 전 종료·한 요청의 복수 생성 작업.
- 기존 공용 pending의 요청별 전환과 서로 다른 TASK 동시 백업/export, 같은 요청 인계 뒤 옛 실행기의 재게시 거절.

### 운영 결정이 필요한 것

- 시험 설정을 바꿀 때 이전 버전으로 진행 중인 학습을 계속할지, 끝난 뒤 어떤 평가/채택에 쓸 수 있을지(K5). 선택한 의미는 AGENTS 약속 8과 함께 명시한다.
- Keeper 결과 모름 후 한 번 재push의 잔여 중복 기동 위험, 야간 신규 요청의 아침 지연을 화면에서 어떻게 안내할지.
- 앱·노트북·rclone이 실제로 어떤 계정 자격으로 파일을 만드는지 확정하고 시스템 입력 권한을 부여할 대상(K3).
- legacy 자산의 실제 등록 경로/관리 책임, stopped 사용자의 실제 Drive/CVAT 자격 회수 절차. 이 항목들은 자동 프로토콜만으로 해결된 것으로 표시하지 않는다.

## 점검했지만 문제가 없던 항목

- 동시성: 기존 경로 이동 폐지, 실행별 버전과 심판 전용 CURRENT 분리, 요청·TASK별 pending 기록, 학습 모델별 잠금.
- 스케줄링: 학습과 관리 일 분리, 실행기 없는 관리 일 비켜 두기, wake_done/signal_done 구분, 야간 미승인 신규 요청의 명시적 지연.
- 복구: 옛 내용을 그대로 덮는 신호 재생 폐지 방향, 새 TASK 응답 불명 시 무조건 재생하지 않음, 채택 대기·확인 필요·복구 참조 자료의 기간 무관 보존.
- 접근: 신뢰된 사용자에게는 실수 방지임을 명시, 모든 입력의 소비자 검사 방향, 실행 의존 파일까지 해시 검증 대상으로 확대, 비밀 저장 위치와 0600 세션 파일 약속 유지.

## 시간이 모자라 보지 못한 항목 및 검증 한계

- 요청한 J1~J10·새 장치 일곱 묶음·알려진 한계 여덟 항목·착수 판단을 모두 다뤘다. 5판까지 해결된 항목과 변경 없는 절의 전면 재검토는 하지 않았다.
