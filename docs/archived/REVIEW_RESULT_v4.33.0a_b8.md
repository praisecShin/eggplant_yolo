# v4.33.0a 검토 결과 — 설계 8판·구현 1a

검토일: 2026-11-14. `AGENTS.md`, `REVIEW_REQUEST_v4.33.0a.md`, `DESIGN_v4.33.md`(8판), `IMPL_STEP1A_v4.33.md`, 구현 점검표와 지정한 신규 코드·시험 네 파일을 읽었다. 결과 경로는 사용자가 지정한 `REVIEW_RESULT_v4.33.0a_b8.md`를 따른다. 파일/줄은 현재 저장소 기준이다.

**판정: 신규 시험 108개·58개는 모두 통과하지만, 1b 연결 전에 판정·권한·중간 장애 복구를 수정해야 한다.** 추가 재현에서 승인 전/격리 중 쓰기 허용, 불완전 식별 보고 수락, 부분 쓰기 후 영구 대기·진행 기록 유실 등을 확인했다. 발견은 M1~M12(치명 4건·높음 8건)이며, 코드 결함과 아직 연결하지 않은 셀/Drive 구현을 구분했다. 비밀 값의 실제 노출이나 실제 원격 데이터 손실을 관찰한 것은 아니다.

코드·노트북·시험·설계서는 수정하지 않았다. 외부 서비스에 접속하지 않았다. 추가 재현과 기존 시험 작업본·로그는 `/tmp`에만 만들었다.

## 3. 설계 8판 판정과 코드 대조 보충

### L1~L3 반영

| L2 소유 계정은 작성 내용 인증이 아님 | 해결(결정 반영). A0 토큰 공유 사실과 세션 지문이 증명이 아닌 실수 방지라는 한계를 명시했다. 서명 도입은 요구하지 않는다. 구현 누락은 M8·M9로 구분했다. |

### 세션 지문과 정상 인계

현재 epoch에서 다른 by_session·표시 없는 assign/lock을 거절하는 방향, G 소유 grant 확인, 서로 다른 지문의 동일 세션을 중복으로 감지하는 구현은 있다. 새 세션 ID에 난수를 넣으므로 정상적인 노트북 사본 별도 실행은 서로 다른 세션으로 처리할 수 있다.

다만 `_judgement_ok`는 구 epoch 파일을 이전 권한 세션인지 검증하지 않고 인계 대상으로 받는다. 이는 이력 자격을 보존하지 않는 현재 설계의 완화된 조건이다. 실행기 함수는 구 epoch 잠금이면 wait_reissue를 반환하므로 곧바로 쓰지는 않지만, 모든 지문 경로에 그 구분을 적용해야 한다(M9). 오래된 진행/인계 파일과 현재 판정을 같은 것으로 취급하지 않는 시험이 필요하다. 같은 세션 ID·같은 기계 지문의 중복 프로세스는 지문만으로 구별되지 않으므로 세션 ID를 매 실행 새로 만드는 규칙이 중요하다.

`reissue`는 TASK lock을 assign보다 먼저 쓴다(888~914행). 새 배정의 assign→lock 순서와 다르므로 실행기는 인계 중 두 파일의 epoch가 맞을 때까지 기다려야 한다. 누락 잠금 복구는 이 차이와 별개로 M5에서 해결해야 한다.

### ReadOnlyProxy의 좁은 쪽

v4.32.0 `cvat_task_tools.py`는 whoami에서 `api_client.users_api.retrieve_self`, 조직 조회에서 `organizations`, 조직 선택에서 `organization_slug` 읽기/설정, export 충돌 복구에서 `task._client`를 사용한다. 현재 허용 목록은 users_api·retrieve_self·organizations 등을 빠뜨려 정상 접속/참조 읽기도 막는다. 조직 범위 선택 같은 client 로컬 설정과 서버 변경을 구분하고 점검표 A의 실제 호출 흐름으로 시험해야 한다. 이름 하나의 전역 목록으로 넓히면 M2의 일반 API 변경 우회가 다시 생긴다. 셀 자체를 아직 전환하지 않은 것은 범위 밖이지만 이 factory의 공용 API 계약은 1b 전에 정해야 한다.

### 신호·같은 회차 상태·선택 흐름

계획→복구 요청→잠금→완료의 일반 신호 순서는 구현됐다. 다만 ConfirmChoice는 recovery_request를 먼저 게시해 격리 잠금 변경 전 외부에 보이게 하므로 실행기는 reserved/current decision까지 확인해야 한다. 생성된 파일과 intake의 증거가 일치하는지, 단순 파일 존재를 완료 증거로 오해하지 않는 시험이 필요하다.

AdoptChoice는 CURRENT와 flag 두 쓰기를 한 효과로 묶는다. CURRENT만 저장하고 종료하면 다음 회차 evidence가 True라 flag가 adopt_wait에 남을 수 있다. 이 역시 효과별 완료 증거/모든 쓰기 prefix 수렴 시험에 포함해야 한다. M7의 입력 변경을 제거한 뒤 시험해야 원격 장애 순서가 정확히 재현된다.

‘모름’의 전체 목록 차단은 일부 구현됐지만 M8 때문에 실패하는 경우가 있다. 관리/학습 needs_check의 사람 선택을 받는 별도 처리도 현재 SIGNAL_KINDS에 없다. ConfirmChoice는 TASK lock만 다룬다. 1b가 실행기/화면만 추가한다고 관리 실종 칸이 풀리지는 않으므로 M10의 종류별 수명 정의에 포함해야 한다.

Keeper의 깨우기 정보는 waiting 다음 확인 시각·관측 시작 시각·요청 ID를 담는다. 그러나 runnable count는 실제 실행기 부재/막힌 TASK·hold를 충분히 반영하지 않아 아직 할 수 없는 일을 즉시 실행 가능으로 셀 수 있다. 실제 Keeper를 붙일 때 이 수를 그대로 반복 push 근거로 쓰지 않도록 실행 가능성과 단순 대기 수를 구분한다.

## 4. 시험의 질과 빠진 확인

기존 108/58개는 신원·기본 FIFO·관리 비켜 두기·학습 호환·대표 신호 중단 등을 확인하지만 **각 Write 경계의 장애 수렴 시험은 아니다.** 현재 crash_after 사용은 소수의 계획/복구 요청 위치에 집중돼 있다. M5·M6의 prefix 반례는 모두 통과한 시험에서 빠져 있었다.

- `tests/test_arbiter_433.py:160`의 `len(a1)==1 and ... or ...`는 괄호 우선순위 때문에 두 번째 TASK 목록 조건만 맞으면 개수 조건을 우회한다. 개수와 내용 단언을 분리해야 한다.
- ‘식별 묶음이 맞는 보고’ 시험(199~209행)은 필요한 epoch/chunk 등을 넣지 않아 불완전 보고 수락을 정상으로 굳힌다(M3).
- access 목록 시험은 요소가 원시 객체인지 보지 않고 길이만 본다(M2). 권한 상실 시험도 실패한 CVAT 호출 직후 복원과 느린 intent 게시를 빠뜨렸다(M4).
- Sim.round는 decide_round가 입력을 수정하지 않는다고 가정한다. 먼저 입력 불변 단언을 추가해야 crash_after가 유효하다(M7).
- asks_handled를 현재 목록과 교집합으로 줄이는 정책은 **목록을 완전히 읽었다는 전제**가 필요하다. 부분 목록/파일 unknown에서 잠시 사라진 보고가 재등장하는 경우를 시험해야 한다. 경로의 basename만 키로 쓰므로 서로 다른 보고가 같은 이름으로 충돌하지 않는 생산 규칙도 필요하다.
- end/result/release/채택/원요청 연결 각각에 대해 모든 쓰기 prefix, 동일 epoch 재시도, 새 epoch 인계, 보고 목록 소실/재등장을 조합하고 정상 실행의 최종 상태와 비교한다. 단순 ‘쓰기가 한 번 나왔다’ 대신 영구 대기·중복 처리·결과 누락이 없는지를 단언한다.

## 5. 1b로 넘어가기 전 구분

### 1b 전에 고칠 것

- **M1~M4:** 권한 상태·완전한 보고 식별·읽기 전용 API 경계·실패 후 복원 차단. CVAT/Drive에 연결하면 위험한 경로이므로 도우미 계약부터 고친다.
- **M5~M7:** 입력 불변과 부분 쓰기의 재조정/결과 보존. 현재 crash_after 시험을 신뢰할 수 있게 만든 뒤 모든 쓰기 경계를 시험한다.
- **M8~M9:** 모름의 fail-closed, 완료된 재시작 인계 표시, 모든 판정 정본의 지문 읽기. 현재 [x]인 지문 검사의 완료 판정도 보완한다.
- **M10~M12:** 작업 유형별 배정/완료·정지 기한·제출 프레임 대응의 공용 스키마와 판정 함수를 닫는다. 실제 작업 실행 함수는 1b/2단계에 남겨도 된다.

### 1b와 함께 고쳐도 되는 것

- 실제 Drive 목록/파일 읽기 실패를 Inputs.unknown으로 정확하게 전달하고, 소유자·세션 지문을 정본 경로별로 적용하는 어댑터.
- CVAT 호출 timeout과 비동기 서버 작업 조회의 실제 연결. `CVAT_CALL_MAX` 상수만으로 timeout은 실행되지 않으므로 호출 계층에서 한도를 적용하고 timeout 후 격리/서버 작업 대조를 시험한다.
- 실제 SDK의 읽기 호출 경로, 관리/취합/생성/학습 작업자 capability, 상태/요청 최종 이름 변경을 새 판정 계약에 연결.
- 단계 기록 새 이름을 재시작 때도 덮지 않도록 작업 번호/기록 번호를 이어가는 방식, 정기 점검의 단계 정체와 unknown 장기화 알림. 현재 periodic_check의 stalled는 빈 목록만 생성하며 실제 검출은 없다.
- Keeper G 해제 신호의 원관리자 신호 검증, 모든 G 입력을 모든 권한의 시스템 입력으로 취급하지 않는 어댑터/판정 연결. 현재 requester_ok는 G를 perm과 무관하게 system:G로 돌려주므로 타입별 허용을 추가해야 한다.

### 운영 결정이 필요한 것

세션 지문을 보안 증명으로 보지 않는 결정, A0 토큰 공유, 야간 신규 요청 지연, CVAT 펜싱 잔여 위험은 이미 명시돼 있으므로 재승인을 요구하지 않는다. 남은 운영 결정은 실제 SDK 참조용 export 허용 범위와 준비할 실행기 capability/자원 수 정도다. 이번 코드 결함을 추가 운영 위험 수용으로 대신하지 않는다.

## 점검했지만 문제가 없던 항목

- L1/L2/L3의 설계 수정과 세션 지문이 실수 방지라는 범위 명시는 반영됐다.
- 신규 시험 166개는 현재 코드에서 모두 통과한다. 비산출물/중간 장애 반례와 별개로 정상적인 대표 경로는 확인한다.
- 실행 컨텍스트는 contextvars와 finally로 회수하고, 배포 해시가 다른 바이트/목록 밖 파일은 거절한다.
- 요청자는 intake로 고정하고 새 배정 시 stopped/권한을 재확인한다. Colab OAuth가 없는 A0 Kaggle을 23번에 배정하지 않는 시험이 있다.
- 새 TASK 빈 후보를 증거 없이 자동 인계하지 않으며, 학습 시작 데이터셋·시험 충돌과 출처 미상 채택 대기를 확인한다.
- 소스의 사용자 정의 예외 메시지는 토큰 값을 직접 기록하지 않는다. 이번 실행에 실제 비밀은 사용하지 않았다.

## 시간이 모자라 보지 못한 항목 및 검증 한계

- 요청서 A~D의 설계 반영·핵심 코드·쓰기 순서·상태 갱신·보고 목록·시험 품질·1b 최소 수정은 모두 다뤘다. 가능한 모든 입력 조합을 완전 탐색한 것은 아니며 위 보충의 추가 시험이 남는다.
- 기존 Python 시험 2개는 numpy 부재, Node 시험 2개는 node 부재, master 계열 3개는 rclone 부재로 통과를 확인하지 못했다. pip/setup.sh도 없어 환경 설치 없이 한계를 기록했다.
- 기존 회귀 시험은 v4.32.0의 /tmp 사본+신규 두 모듈에서 실행했다. 실제 새로운 마스터/작업자/앱 연결 검증은 아니다.
- 실제 Drive·CVAT·Kaggle·Apps Script API/지연·소유자 동작은 범위 밖이다. ReadOnlyProxy 재현에는 네트워크 없는 가짜 객체를 썼다.
- 1b/2단계의 미구현 셀 전환 자체, 저장소 밖 앱 코드, F7·F8은 결함으로 집계하지 않았다.
